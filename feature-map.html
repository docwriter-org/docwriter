Data Structures

The One Document Schema: AtomzFileV2

Everything revolves around this format. It's what document.atomz stores, what the client sends to the server, and what the server sends back. The four top-level fields map 1:1 to the four canonical in-memory stores.

AtomzFileV2 = {
  version: 2,
  atoms: [{ id, subject, predicate, children: Atom[], transition? }],   ← atoms store
  rules: [{ id, text }],                                                 ← rules store
  blocks: [                                                               ← blocks store
    { id, type:'heading', level:1|2|3, text }
    { id, type:'markdown', markdown, atomIds:string[] }
  ],
  pins?: [{ id, kind:'verbatim', value, anchors:[{type:'atom'|'block', atomId|blockId}] }]  ← pins store
}

The Render Projection: RenderDocument

A flattened view of AtomzFileV2 that the agent edits via .atomz-render.json. The agent can edit both atoms and prose. Headings are included — agent can edit or add them.

RenderDocument = {
  atoms: [{ id, subject, predicate, pinnedWords?[], children }],  ← pinnedWords inlined from pins
  rules: ["rule text", ...],                                       ← flattened to strings
  prose: [{ id:0, frags:["atomId",...], para:0, text:"..." }]     ← blocks flattened to sentences
}
// prose entries with text starting with "# " are headings
// agent can Edit "text" values AND atom "subject"/"predicate" values

In-Memory Stores

Canonical Stores writable, source of truth

These four stores ARE the document while the app is running. All user mutations go through these. After mutating, call reproject() to update derived views. On save, these four stores are serialized to AtomzFileV2 and written to disk.

StoreTypeWhat It Holds
atoms Atom[]
{ id, subject, predicate, children: Atom[], pinnedWords?, transition? }		 The meaning layer. Each atom = one claim. subject = what the sentence is about, predicate = the claim. Can have sub-atoms (children). pinnedWords is derived from pins by reproject(), not set directly. Serialized to document.atomz → atoms.
blocks AtomzBlock[]
heading: { id, type:'heading', level, text }
markdown: { id, type:'markdown', markdown, atomIds[] }		 The presentation layer. Ordered list = document order. Heading blocks = section titles. Markdown blocks = prose paragraphs, each linking to atoms via atomIds. The TipTap editor reads/writes these directly. Serialized to document.atomz → blocks.
pins AtomzPin[]
{ id, kind:'verbatim', value, anchors[] }
anchor: { type:'atom', atomId } or { type:'block', blockId }		 "This word must appear verbatim in rendered prose." Anchored to atoms (pinned from atom pane), blocks (pinned from editor), or both. Serialized to document.atomz → pins.
rules Rule[]
{ id, text }		 Writing constraints the agent must obey. Checked by validation hooks after each agent Edit. Serialized to document.atomz → rules.

Projected Stores readonly, auto-derived

Computed from canonical stores by reproject(). No component ever writes to these. They exist so UI components can read convenient shapes (sentences, paragraph breaks, etc.) without parsing blocks directly. Not serialized to disk — always recomputed.

StoreTypeDerived FromWhat It Is
prose Sentence[]
{ text, frags: atomId[], para }		 blocks Each markdown block → one sentence. frags = the atom IDs this sentence renders. para = paragraph index. Used for bidirectional highlighting and diff display.
sections Section[]
{ title, beforeAtomIndex }		 blocks + atoms Heading blocks extracted with their position relative to atoms. Used for section editing UI in atom pane.
paraBreaks Set<number> blocks + atoms Atom indices where a new paragraph starts. Used for the paragraph break toggle buttons.
editorPins EditorPin[]
{ text, para }		 blocks + pins Block-anchored pins mapped to paragraph numbers. Used to render pin highlights in the editor.

Disk Files

All writes use atomic rename (write to .tmp then rename) so a crash never leaves a corrupt file.

FileSchemaWhat It IsLifecycle
document.atomz AtomzFileV2
{ version:2, atoms[], rules[], blocks[], pins?[] }		 The saved document. Single source of truth on disk. Maps 1:1 to the four canonical in-memory stores. Read: on page load → hydrates all stores.
Written: only by server endpoints (render, atomize) after merging agent edits. Client never writes this file. Atomic writes (tmp + rename).
.atomz-render.json RenderDocument
{ atoms[] (with pinnedWords), rules: string[], prose[] }		 Temporary working copy for the agent. Different schema from document.atomz because the agent needs a flat prose array to edit with its Edit tool, not the block structure. Headings stripped so agent can't touch them. Created: at start of each render (server projects AtomzFileV2 → RenderDocument, strips headings, writes file).
Edited: by agent during render (Read + Edit tools).
Read back: by server after agent finishes → re-inserts headings → merges back into AtomzFileV2 → writes document.atomz.
Throwaway: stale between renders, never read by client.
.atomz-ops.jsonl Append-only JSONL (WAL) Write-ahead log of user intents. Two line types:
enqueue: { event:"enqueue_document_op", op: DocumentOp } — "user did X"
resolve: { event:"resolve_document_ops", ids[], resolvedAt } — "X was processed"
On refresh, scan the log: ops that were enqueued but never resolved are replayed.		 Append: client POSTs new ops, server appends enqueue lines. After processing, client PATCHes, server appends resolve line.
Read: on page load, GET returns only unresolved ops.
.atomz-state.json { sessionId?: string } Claude Agent SDK session ID. Resuming a session lets the agent remember prior context without a cold start (~1.8s saved). Set: when agent returns a new session ID. Cleared: by "New Session" button. Read: at each render to decide whether to resume or start fresh.
.atomz-history.json Array<{ timestamp, trigger, prose[] }> Version snapshots for the history UI. Captures prose state before each agent render. Max 30 entries (oldest trimmed). Written: by render endpoint at start of each render. Read: by client for version diff/restore UI.

Agent Render Flow

What happens when an op needs the agent. The agent edits a projected working copy (.atomz-render.json), then a deterministic merge algorithm converts the edits back to AtomzFileV2.

StepWhoWhat Happens
1. Send request Client POST /api/render with { documentJson: AtomzFileV2, model, trigger }
2. Project Server projectAtomzFileToRenderDocument() converts AtomzFileV2 → RenderDocument. Inlines pinnedWords from pins onto atoms. Flattens blocks to prose array. Flattens rules to strings.
3. Write working copy Server Writes RenderDocument to .atomz-render.json. This is a throwaway file — if agent corrupts it, document.atomz is safe.
4. Agent edits Agent Agent uses Read to see the file, Edit to change values. Can edit:
• Prose: change "text" values in the prose array
• Atoms: change "subject" or "predicate" on atoms
• Headings: edit or add prose entries starting with #
Each Edit is validated by hooks that check pinned words and rules.
5. Merge Server (algorithm) mergeRenderDocumentIntoAtomzFile(canonicalFile, editedRenderDoc):
• Takes atoms from edited render doc (agent may have changed them), strips pinnedWords
• Converts each prose entry back to a block (heading text → heading block, other → markdown block)
• Takes rules from the original canonical file (agent can't change rules)
• Takes pins from the original canonical file (agent can't change pins directly)
This is a deterministic algorithm, not an AI step.
6. Commit Server Writes merged AtomzFileV2 to document.atomz atomically (tmp + rename).
7. Deliver Server → Client SSE result event with merged AtomzFileV2. Client calls applyCanonicalFileToStores() to update all in-memory stores.

Consistency & Reliability

Normal Flows

FlowSteps
User edits an atom 1. atoms.update() in memory → reproject() → UI refreshes
2. pushDocumentOp({ type: 'edit_atom' }) → persisted to WAL
3. 1500ms: op processor ensures all ops in WAL → sends to agent → agent updates prose → server writes document.atomz → resolves ops → WAL compacted
User edits prose in editor 1. 10s idle → syncEditorToBlocks() → blocks.set() → reproject()
2. pushDocumentOp({ type: 'update_blocks', source: 'editor' }) → WAL
3. 1500ms: op processor → agent examines edits, updates atoms to match
User toggles paragraph break 1. Split/merge markdown blocks → blocks.set() → reproject()
2. pushDocumentOp({ type: 'update_blocks', source: 'structure' }) → WAL
3. 1500ms: op processor → agent reviews structure, adjusts transitions if needed
Page refresh 1. GET /api/document → load document.atomz → hydrate all stores
2. GET /api/document-ops → server scans WAL, returns unresolved ops
3. Replay each op → reproject()
4. Resume op processing (triggers agent for unresolved ops)

Who Writes What

FileWriterWhen
document.atomzServer endpoints only (render, atomize)After agent finishes and merge completes, before sending result to client. Client never writes this. Atomic writes (tmp + rename).

Crash Recovery

ScenarioRecovery
Crash before agent finishesdocument.atomz unchanged (agent only edits the throwaway .atomz-render.json). Unresolved ops replay from WAL on refresh → triggers agent again.
Crash after agent finishes, before client receivesRender endpoint already wrote merged result to document.atomz. Client loads updated doc on refresh. Ops may replay but agent sees the document is already up to date.
Crash during file writeAll writes use atomic rename (write .tmp → rename). Never a partial/corrupt file.
User edits during renderUser edits are recorded as ops in the WAL. After agent result is applied, any ops pushed during the render are replayed on top of the agent's result — user edits are not lost.

Consistency Guarantees

GuaranteeHow
Single writer to document.atomzOnly server endpoints (render, atomize) write it, using atomic writes (tmp + rename). Server writes before sending result to client. Client never writes.
Ops durable before processingOp processor verifies all ops are persisted to WAL before sending to agent. If any persist fails, processing stops — no agent render on un-persisted ops.
User edits survive rendersOps pushed during a render are detected (by comparing op IDs before vs after) and replayed on top of the agent result.
Block IDs stable across rendersEach prose entry in the render document carries its source block ID. Merge matches by ID, not position or content. Agent reordering preserves IDs.
Orphaned pins cleaned upMerge filters out pin anchors pointing to deleted atoms or blocks. Pins with no anchors left are removed.
All ops go to agentNo "local-only" ops. Every user action is sent to the agent. Agent decides what needs changing.
WAL compactedAfter resolving ops, WAL is rewritten with only unresolved ops. Prevents unbounded growth.
No concurrent rendersOnly one render at a time. New render aborts previous via AbortController. Op processor uses a while loop with isProcessing guard — no re-entrance.
Undo aborts renderCmd+Z cancels any in-flight render before restoring blocks, so the agent result can't overwrite the undo.

Design Decisions

DecisionRationale
Rules are user-onlyThe agent obeys rules but cannot add or modify them. Rules are the user's constraints on the agent — the agent shouldn't change its own constraints.
Pins are user-onlyThe agent ensures pinned words appear in prose, but cannot create or remove pins. Pins represent the user's intent about what must be preserved verbatim.

Agent Render Flow

What happens when an agent-needed op is processed

StepDetail
1. Build requestCanonical stores → serialized to AtomzFileV2. Sent to server with model + trigger string.
2. Server preparesNormalize file → project to RenderDocument (atoms with pinnedWords, prose with block IDs, rules as strings) → write .atomz-render.json
3. Agent runsClaude with tools (Read/Edit for edits, +Skill/Agent for full renders) against the render file. Can edit prose text, atom subject/predicate, and headings.
4. Validation hooksAfter each Edit tool call: check pinned words appear, check rules. Agent must fix violations.
5. Server mergesRead edited file → deterministic merge back to AtomzFileV2 (matches blocks by ID, cleans orphaned pins) → atomic write to document.atomz
6. SSE resultServer sends merged AtomzFileV2 to client. Client calls applyCanonicalFileToStores(result). Replays any ops pushed during render.
7. CleanupStale annotations cleared, versions reloaded, ops resolved in WAL, WAL compacted.
