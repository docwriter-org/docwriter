DocWriter · Engineering Overview

A local-first writing editor with an agent that works on a shadow copy.

DocWriter edits real files in a real folder on disk. Each open tab is backed by its own CRDT document in the browser. When the user pauses, a Claude agent wakes up, edits a shadow copy of the files on disk, and the app merges the agent’s output back into the live document without clobbering anything the user typed in the meantime.

SvelteKit + Tiptap Yjs per tab IndexedDB Claude Agent SDK SSE streaming 3-way merge
Section 1

At a glance

Four processes, one folder. The browser holds the live document state. The server mediates file I/O and runs the agent. The agent reads the workspace and writes only to shadow files. The disk is the source of portability, not the source of truth.

Core invariant

Live state lives in the browser’s Y.Doc. Disk files are a portable mirror. Shadow files are transient workspace for the agent. The merge algorithm reconciles shadow → live without losing user keystrokes.

Section 2

Mental model: three worlds

Vocabulary (used everywhere below)
  • Render. One full agent cycle: the user pauses (or clicks Wake), the server calls the Claude Agent SDK once, the agent reads files and edits shadow copies, the result streams back, the browser merges it into the editor. Begins when the user triggers it; ends when the SDK emits a final result. Named after /api/render. You can think of it as "agent turn" or "agent run."
  • Shadow. A throwaway copy of a workspace file under .docwriter/agent/<path>. Created at the start of a render, edited by the agent, read and deleted at the end. The agent never touches the real file.
  • Review round. One apply of agent edits into the live document, shown in the UI as a card with Accept / Reject. A single render can produce multiple review rounds (streaming incremental applies + a final apply).
  • Live / Disk / Shadow. The three copies of each document (defined in the table below). When code says "Live" it means the Y.Doc in the browser, not the file on disk.

The single hardest thing to hold in your head about DocWriter is that there are three copies of every document during an agent render, and they can diverge. If you understand how they’re kept in sync, the rest of the system falls out naturally.

WorldWhere it livesWhat it isWho writes to it
Live Y.Doc in memory
mirrored to IndexedDB		 The CRDT the editor actually renders. One per open tab. Truth for everything the user sees and edits right now. User keystrokes · agent apply step
Disk Real file under DOCWRITER_ROOT Portable, git-friendly copy of the document. Autosaved from Live on a debounce. This is what you see if you cat the file. Autosave · external editors (via --watch)
Shadow .docwriter/agent/<tab-path> Transient copy made at the start of each render. The agent’s Edit/Write tools operate on this file, not the real one. Reset from Disk at render start · edited by agent · re-synced from user edits mid-render
Why three?

The Claude Agent SDK’s file-editing tools need a real filesystem path. They can’t operate on a Y.Doc. If we pointed them at the real file, concurrent user typing would race with agent writes and one side would lose. The shadow decouples them: the agent gets a stable file to edit, and the app decides how and when to fold the result back into Live.

Section 3

What the user does

Before you read any code, picture an actual writing session. Every architectural decision earns its keep against this workflow.

  1. Launch against a folder. The user runs docwriter pointed at a workspace directory. The CLI sets DOCWRITER_ROOT, starts the SvelteKit server, and opens the browser.
  2. Open a file. The file tree lists the workspace. Clicking a file opens it as a tab. The browser creates (or rehydrates from IndexedDB) a Y.Doc for that tab and mounts Tiptap on it.
  3. Write. Every keystroke updates the Y.Doc. Two independent timers also run in the background, both reset on every keystroke so they only fire when you actually pause:
    • Autosave (~50ms): after a 50ms pause, the current markdown is written to the file on disk via PUT /api/document. Keeps the file up to date so the server always has fresh content.
    • Idle-submit (3s): after a full 3 seconds of quiet, submit() runs and kicks off a render — the agent wakes up. Press Cmd/Ctrl + Enter to skip the 3-second wait and trigger it now.
    "Debounced" here means the timer restarts every time you type, so it only fires after you stop — like a motion light that turns on only once you’ve been still for a bit.
  4. Agent wakes. The right-hand history pane streams the agent’s thinking, tool calls, and progress live over SSE. The user can keep typing while this happens.
  5. Review proposal. When the agent finishes, the proposed edits land in the editor as a diff overlay (if track-changes is on) or merge silently. Pending rounds appear as cards in the left pane with Accept and Reject.
  6. Accept, reject, or keep writing. Accept keeps the merge. Reject rewinds just the agent’s edits and leaves user edits untouched. Ignoring the review and typing over it is also fine — the overlap-safe merge protects user keystrokes even in that case.

Section 5 · Data flow

Flow: the user types a character

Primer: Tiptap, ProseMirror, transactions
  • ProseMirror is the low-level editor engine. Tiptap is a friendlier wrapper around it. DocWriter uses Tiptap; under the hood it’s all ProseMirror.
  • The document never changes directly. To change it, something creates a transaction — an object describing the change (e.g. "insert 'h' at position 5") — and hands it to the editor. The editor applies it, updates the document, then calls your onUpdate callback. One transaction = one change = one onUpdate call.
  • Transactions can carry metadata. The code that creates a transaction can attach extra info with tr.setMeta(key, value). Think of it as a sticky note: "this transaction came from X." The receiver reads it with tr.getMeta(key).
  • Who creates transactions here? Three different sources, and the handler has to behave differently for each:
    1. User keystrokes — no metadata. Save to disk, restart timers, record the edit range.
    2. Agent applies — tagged with Yjs origin 'agent' (set by yjs-agent.ts when it applies the merged markdown). Save to disk, but don’t restart the idle timer (an agent edit shouldn’t reset "the user is done writing").
    3. Yjs restore — tagged with ySyncPluginKey (set by y-prosemirror when it pushes content from IndexedDB or a remote update into the editor). Skip everything — this isn’t a real change, just the editor catching up to its stored state.

With that vocabulary, the whole update handler in TiptapEditor.svelte is just a series of "is this transaction X? then do Y" checks, in order.

  1. Tiptap calls onUpdate(transaction). Something just changed the document. The transaction object has a .getMeta() method we can query to figure out who made it. At this point we don’t know yet — it could be any of the three sources above.
  2. Check for the Yjs restore marker; if present, return early.

    Concretely: if (transaction.getMeta(ySyncPluginKey) !== undefined) return;. That marker is attached by y-prosemirror any time it pushes content into the editor as part of restoring the Y.Doc — for example, when IndexedDB finishes loading your saved document on page reload and the content gets pumped back into the editor piece by piece. Each of those pieces fires onUpdate. If we didn’t bail out here, the handler would serialize whatever partial content is in the editor right now (possibly an empty string, if we caught it mid-restore) and autosave that to disk — wiping your real file. So: if the marker is there, do nothing. Let the restore finish in peace.

  3. Serialize the current editor content to markdown (or plain text). Markdown tabs run a markdown serializer; plain tabs (.txt, .json, source code) use a schema that just emits raw text. Result is a string, e.g. "# Hello\n\nworld".
  4. Update the userMd store and debounce a disk write.

    userMd is a Svelte store (writable<string>('')) holding the latest serialized markdown. Multiple readers subscribe to it — the outline pane rebuilds on heading changes, the autosave loop reads what to write, the initial-tab-open flow seeds the Y.Doc from it, and baseline/diff paths sample it.

    Why materialize this as a store instead of serializing on demand? Two reasons:

    • Reactivity. Subscribers re-run automatically when the markdown changes. A getCurrentMarkdown(tabId) function wouldn’t give you that — each reader would need its own Y.Doc observer or poll.
    • Shared computation. ProseMirror → markdown serialization isn’t free. The editor has to compute it here anyway (to feed autosave), so publishing the result once amortizes it across every reader instead of each of them re-serializing.

    After updating the store, schedule a PUT /api/document request ~50ms from now. If another keystroke arrives in that window, the scheduled request is cancelled and re-scheduled — so we only actually write to disk once the user pauses. After the write, the file on disk matches Live.

  5. Check for the agent-apply origin; if present, stop here.

    We check the Yjs transaction origin (separate from ProseMirror’s metadata — Yjs has its own concept). If it’s 'agent', this change came from yjs-agent.ts applying a merged agent proposal. We still wanted the disk write (step 4) so the file reflects the new content, but we don’t want to treat it as user activity: no idle-timer restart. Return.

  6. Restart the 3-second idle-submit countdown. Clear any existing idle timer, start a new one. If 3 seconds pass with no further onUpdate calls, the callback fires submit() — which is the entry point for a render. Pressing Cmd/Ctrl + Enter skips the wait and calls submit() immediately.
Section 6 · Data flow

Flow: triggering an agent render

A render is one agent turn. Something in the browser triggers it, the server makes one streaming call to the Claude Agent SDK, the agent edits shadow files, and a stream of events flows back to the browser while it’s all happening.

What can trigger a render

Any of these ends up calling the same submit() function in the browser, which POSTs to /api/render. The trigger only determines the explicit user prompt (userMessage) — everything else the agent sees is the same regardless.

TriggerWhat the user diduserMessage sent
Idle timeoutTyped, then paused 3 secondsEmpty. Server substitutes "the user clicked Wake-up without a specific request."
Keyboard shortcutCmd/Ctrl + EnterEmpty (same as idle, but no wait).
Wake buttonClicked the cat in the agent dockEmpty.
Selection feedbackSelected text, picked a pinned action or typed a note in the popupThe action label / note, plus the excerpt and range as context.
Direct messageOpened the agent dock composer and typed a requestWhatever they typed.

What the POST body actually contains

The body is small because the server assembles most of the context itself by reading state.json, the shadow directory, and the current files.

POST /api/render
{
  userMessage:       string     // empty for idle / wake-up, or the user's prompt
  model:             'opus' | 'sonnet' | 'haiku'
  tab:               string     // which tab is active
  warmup?:           boolean    // optional prefetch flag
}

Rules, references, agency setting, and the current tab content are not in the POST body — the server reads all of that from disk, including previous "last agent view" shadow state for diffing. That’s why adding a rule or editing a style reference takes effect on the very next render without the client doing anything special.

Step-by-step

  1. Browser calls POST /api/render. The response isn’t a single JSON blob — it’s an SSE stream the browser subscribes to. The stream will stay open for seconds to minutes while the agent works.
  2. Server reads prior shadows, then snapshots all open tabs into fresh shadows.

    Before the reset, the existing shadow file is treated as the previous "last agent view" for that tab and used to build the diff block. Then resetAllAgentDocs() copies every open tab from its real workspace path into .docwriter/agent/<tab-path>. After this, shadow content exactly matches Live content and becomes the baseline for the 3-way merge at the end of the render — it’s how the app tells "what the agent changed" apart from "what the user typed during the render."

  3. Server builds one big prompt.

    Assembled in buildMultiTabPrompt(). Regardless of trigger, every render prompt contains the same sections — only userMessage varies with how the render was triggered.

    What goes in:

    • The userMessage (from the POST body), or a default substitute if empty: "the user clicked Wake-up without a specific request."
    • Current content of every open tab, inlined as fenced code blocks, with the active tab flagged so the agent knows where attention should default. Read fresh from the shadow directory (which is a copy of disk at render start).
    • A per-tab diff since the agent last edited that file. The server compares the current file on disk against the persisted shadow from the previous render and inlines a unified diff under the file. This is how "I fixed a typo the agent missed" or "I reverted that last rewrite" surfaces to the next render as a visible change the agent can react to.
    • All persistent writing rules, freshly read from state.json → rules at render start. Add a rule between renders and the next render picks it up automatically.
    • Style references, assembled by buildStyleReferencesPromptBlock() — also read fresh each render.
    • Agency guidance — a paragraph that varies with agentSettings.agency (conservative / balanced / aggressive) and rewires "when is it OK to make an edit?"
    • Tool sandbox rules — only write inside .docwriter/agent/ shadows and scratch; propose rules and hooks via MCP tools instead of editing config directly.
    • MCP tool definitions for propose_rule and propose_hook, so the agent can suggest new rules/hooks for the user to review in the sidebar.

    Why re-send all of this every render?

    DocWriter does resume the SDK session across renders (resume: currentSessionId is passed to query()), so conversation history carries forward. Reasonable question why we also re-include rules, references, and sandbox text in every single turn. Four reasons:

    1. Those things change between renders. The user can add a rule, toggle agency, or edit a reference at any moment. Re-reading from disk each render is the simplest way to always reflect current state; tracking deltas would add complexity with no real upside.
    2. Session resumption preserves conversation history, not working state. It remembers "5 turns ago you rewrote paragraph 3," not "the current ruleset is X." Files, rules, and agency may all be different now — each turn’s prompt is the place for "here’s the world right now."
    3. Long sessions drift. By turn 50 the model may have internally summarized earlier context. Rules sent only at turn 1 could fade out of active attention. Re-including them keeps them in the foreground.
    4. Prompt caching makes it cheap. Stable prefixes are cached by the API, so wire cost is real but inference cost is mostly amortized. Re-sending isn’t the bandwidth problem it looks like at first glance.
  4. Server calls the SDK’s query() with that prompt. The agent is given access to Read, Edit, and Write tools, but the file paths it’s allowed to touch are restricted to the shadow directory. It can read anywhere in the workspace, but it can only write inside .docwriter/agent/.
  5. Before every agent write, a pre-tool hook re-syncs user edits into the shadow.

    The agent takes seconds to minutes. The user may keep typing the whole time. Autosave is writing those keystrokes to the real file on disk every ~50ms. But the agent is looking at the shadow, which was snapshotted at render start — it’s getting stale. So just before each Edit/Write the agent tries to run, syncUserEditsToAgent() reads the current real file and overwrites the shadow with it. The agent’s edit is then computed against the freshest user content. This is what keeps "keep typing while the agent runs" from producing stale proposals.

  6. The server streams events down the SSE connection as the agent works.

    Each event is a small JSON object with a type field. Event kinds include:

    • tool_call_start, tool_call — the agent invoked a tool (shown in the history pane).
    • assistant_text, assistant_thinking — model output and thinking summaries.
    • incremental_apply — the shadow just changed; push this intermediate version to the editor through the 3-way merge so the user sees each edit land in real time. See step 7 for the merge mechanics.
    • rule_proposal, hook_proposal, ask_user — sidebar UI events.
    • notification, cost — status updates.
    • result — the render is done; this carries the final shadow content per tab.
  7. Every incremental_apply runs the 3-way merge, against a rolling baseline.

    This is the part that keeps the editor in sync with user typing during streaming — no drift accumulates waiting for result.

    Two baselines are tracked per render, for two different purposes:

    • mergeBaseByTab[tabId] — the merge baseline (markdown string). Initialized at render start from preRenderMdByTab, so the first incremental apply sees the pre-render user content as base. This is intentional: if the user typed during the agent’s thinking, those keystrokes show up as user hunks in the base → current diff. Those hunks are what let the merge detect overlap and protect user edits. If we captured base at first-apply time instead, the user’s mid-render typing would be baked into base and invisible to overlap detection.
    • baselineStates — the reject baseline (Y.Doc snapshot). Captured at render start via captureBaselineForAgent(tabId), then re-captured on the first incremental_apply for each tab (line 687 in +page.svelte). Why re-capture? Reject needs to rewind only the agent’s edits, not the user’s mid-render typing. So the reject baseline should be "Y.Doc state right before the first agent edit lands" — which by then includes whatever the user typed. User typing survives reject; agent edits don’t.

    How the merge baseline rolls forward across applies:

    • First incremental apply for a tab: applyAgentMarkdown(tabId, agentMd, trackChanges=true, ..., mergeBaseByTab[tabId]) runs a 3-way merge of (pre-render base, current Live, agentMd) and commits to the Y.Doc with origin 'agent'. After the apply, mergeBaseByTab[tabId] = iAgentMd.
    • Each subsequent incremental apply: baseline = previous incremental’s agentMd. The diff is now "what the agent changed since its last step," merged against whatever the user has typed since. Overlap-safe at every step.
    • Each apply adds its own Yjs undo step (agent origin), tallied into incrementalStepCountByTab[tabId]. These steps will all belong to the review round created at result.
    • Conflicts accumulate into conflictCountByTab[tabId] across all incremental applies for this render — used at result to decide whether to queue a retry.
  8. On result, finalize: one last merge + create the review round.

    Why a final apply is still needed after all those incremental ones: the agent’s final shadow state can differ from the last incremental_apply (e.g. a Write after the last Edit). The final call to applyAgentMarkdown(agentMd, ..., baseline=mergeBaseByTab[tabId]) canonicalizes: if the last incremental already matched the final shadow it’s a no-op; otherwise it commits the remaining delta (plus one more undo step).

    Then the review round is born. In track-changes mode, a PendingReviewRound is added to the tab’s Yjs review map with afterMd = final agentMd, beforeMd = captured pre-render state, and stepCount = streamedSteps + 1. Reject uses that count to rewind exactly the right number of steps from the agent-only UndoManager.

    In silent mode the apply runs with origin ySyncPluginKey instead of 'agent' (no review round, no agent UndoManager capture). Shadow files are cleaned up on accept (or, post-refactor, kept around as "last agent view"; see §6’s POST body note).

Section 7 · Data flow

Flow: review & accept/reject

Track-changes mode turns each successful apply into a PendingReviewRound stored in the tab’s Yjs review map. Silent mode skips the round entirely and just merges.

What a review round contains

PendingReviewRound {
  beforeMd        // baseline markdown before the round
  afterMd         // merged markdown after the round
  trigger         // 'idle' | 'manual' | 'feedback' | ...
  timestamp
  sizeClass       // 'tiny' | 'big'  — drives UI treatment
  stepCount       // how many Yjs undo steps belong to this round
}

stepCount is the non-obvious one. A single render can produce multiple incremental_apply events plus a final result apply — each is its own Yjs transaction on the undo stack. Reject needs that count to rewind exactly the right number of steps.

Accept
  • Drop the round from the review map.
  • Leave the merged content in the live Y.Doc.
  • POST /api/document with action: accept deletes the shadow file.
Reject
  • A dedicated Y.UndoManager tracks only transactions with origin agent.
  • Rewind exactly stepCount steps — this undoes agent edits without touching user edits that landed during the render.
  • If the undo stack is gone (post-refresh), fall back to re-applying the stored beforeMd baseline.
Section 8 · Data flow

Flow: conflict & automatic retry

The interesting case is when the agent’s proposal and the user’s keystrokes touch the same paragraph. The 3-way merge decides what to do. 

base    = shadow contents at render start (or previous agent step)
current = live user document now (includes edits typed during render)
agent   = final shadow contents from the agent
  1. Diff twice. mergeAgentEditsIntoCurrent() computes hunks from base → current (the user’s edits) and from base → agent (the agent’s edits).
  2. For each agent hunk, check overlap. If it overlaps any user hunk in base coordinates, skip it and bump conflictCount. Otherwise apply it to the current token stream, adjusting indices for earlier applied offsets.
  3. Return { mergedText, appliedHunks, conflictCount }. The apply path uses mergedText as the new content.
  4. If conflictCount > 0, queue one automatic retry. A history notification is emitted. The retry runs against the updated document and is marked internally so it can’t loop forever.
Design call

The merge favors the user. We never silently overwrite user keystrokes to make the agent’s diff cleaner. If a round applies only half of the proposed edits, that’s the correct outcome — surface the conflict and let a fresh retry handle it with current context.

Section 9 · Design

Why the filesystem shadows exist

The Claude Agent SDK exposes Edit and Write tools that take real filesystem paths and perform real I/O. There is no way to hand it a Y.Doc handle. That constraint drives the shadow design.

Option A — point agent at real file

The agent writes directly to draft.md. The browser’s Y.Doc and the disk file now disagree any time the user is typing. Autosave races with agent writes. Either side clobbers the other. Review is impossible because there’s no stable “before” to diff against.

Option B — shadow copy (what we do)

Copy the file to .docwriter/agent/<path> at render start. Agent edits the shadow; real file is untouched by the agent. At render end, the app reads the shadow, merges it against current Live state, and applies the result as Yjs ops. The shadow is the baseline for the 3-way merge and for rejection.

Shadows also let the pre-tool hook sync user edits into the shadow between agent steps — so the agent’s next Edit sees what the user just typed, without having to pause the agent or lock the document.

Persistence layers

DocWriter persists state in three places with clearly separated responsibilities. Nothing is duplicated; each layer answers a different question.

Rehydration order

On reload, the browser reads each tab’s Y.Doc from IndexedDB before asking the server for document content. This is why refreshes feel instant and why in-progress review rounds survive page reloads. The y-prosemirror sync transactions that fire during this hydration are exactly the ones flow-typing skips.

Section 11

Merge & review internals

The apply path (src/lib/yjs-agent.ts)

  1. Run the 3-way merge between render-start baseline, current Live content, and the agent’s final shadow markdown. Output is mergedText.
  2. Parse mergedText into ProseMirror JSON using the active tab’s schema (markdown or plain).
  3. Compute the minimal changed range between current editor doc and the parsed target. Dispatch a single replace(from, to, newSlice) transaction rather than replacing the whole document — this keeps cursor position, selection, and collaborative ops tight.
  4. Wrap it in a Yjs transaction with an explicit origin:
    • 'agent' — review mode. The agent-only UndoManager captures this, enabling precise reject.
    • ySyncPluginKey — silent mode. Merges with the user’s normal undo stack and the editor update handler ignores it (see flow-typing).

3-way merge algorithm (src/lib/three-way-merge.ts)

Tokens are roughly words/whitespace/punctuation — not characters. diff builds hunks.

mergeAgentEditsIntoCurrent(base, current, agent):
  userHunks  = diff(base → current)
  agentHunks = diff(base → agent)

  for each agentHunk:
    if any userHunk overlaps agentHunk in base coordinates:
      conflictCount++
      skip
    else:
      apply agentHunk to current token stream
      track offset for subsequent hunks
      appliedHunks++

  return { mergedText, appliedHunks, conflictCount }

Review rounds

Stored in the tab’s Yjs review map, so they’re local-first and survive reload. The diff overlay composes all pending rounds against the earliest baseline — i.e. multiple back-to-back renders show as one cumulative diff, not a stack.

Undo isolation

A second Y.UndoManager is constructed with trackedOrigins: new Set(['agent']). It captures agent apply transactions but ignores user keystrokes. Reject calls undo() on it stepCount times, which rewinds exactly the agent’s edits and leaves anything the user typed during the render intact.

Section 14

Workspace safety

File APIs all route through src/lib/server/workspace-path.ts, which resolves any request path and validates it stays inside DOCWRITER_ROOT.

  • Path traversal (../../etc/passwd) is rejected.
  • Symlink escapes are blocked — even for paths that don’t exist yet, the resolver walks up to the nearest existing ancestor, resolves its real path, and checks containment from there.
  • Hook configuration is never agent-writable. The agent can only propose hooks via the propose_hook MCP tool; acceptance flows through the user and PUT /api/hooks.

Bottom line

DocWriter is a local, multi-file writing environment with per-tab CRDT editor state, a filesystem shadow workspace for the agent, a streaming render loop, a review queue, and conflict-aware merge logic that favors the user’s live edits. The shadow / merge / review triangle is what lets the agent use real file-edit tools without the app ever feeling like it’s fighting you.
