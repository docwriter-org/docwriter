    01 Start here

    What is DocWriter?

    DocWriter is a local markdown writing editor with an AI side‑channel. You type in a Tiptap editor; an agent proposes edits by mutating the same live document you're looking at. Every change — yours or the agent's — flows through a single origin‑tagged CRDT log on the server.

    This walkthrough is meant to take you from zero to "I could navigate this codebase on my own." Each step is one concept. Hit → (or Space) to advance. The TOC on the left lets you jump around.

    SvelteKit + Svelte 5 runes Tiptap editor Yjs CRDT Hocuspocus WS SQLite (better‑sqlite3) Claude Agent SDK MCP tools
    Rule of thumb while reading: if you're ever confused about where something lives, the answer is almost always "the server Y.Doc." Every other layer is a projection of it.
    02 Core invariant

    The one big idea

    Hocuspocus owns each tab's Y.Doc on the server. Everything is just a Yjs transaction with an origin tag.

    • The browser is a synced client, not an owner — it binds Tiptap to a HocuspocusProvider over a WebSocket.
    • The agent is another client — its MCP tools open a DirectConnection and transact(..., AGENT_ORIGIN) on the same doc.
    • User keystrokes land as USER_ORIGIN. Cold‑start seeds land as SYSTEM_ORIGIN.
    • Every transaction is appended to SQLite's yjs_updates with its origin, and broadcast to every other client.

    Review, undo, reject, and "what did the agent just do?" all fall out of origin tagging on one authoritative doc. There are no shadow files, no 3‑way merge, no client IndexedDB.

    03 What runs where

    Processes and ports

    When you run docwriter in a workspace, one Node process starts and hosts two servers on different ports:

    • SvelteKit HTTP on PORT — renders the page, hosts /api/* endpoints.
    • Hocuspocus WebSocket on DOCWRITER_WS_PORT (default 3001) — the Y.Doc sync channel.

    The Agent SDK loop is spawned per render inside that same process — it's not a separate service. It talks to Hocuspocus through an in‑process DirectConnection, not the WebSocket.

    05 Data model

    What's inside a Y.Doc

    Every tab has exactly one Y.Doc with two shared types. Defined once in src/lib/shared/ydoc-codec.ts and reused by server and client so the schema can never drift.

    classDiagram
  class YDoc {
    XmlFragment 'default'
    YArray 'rounds'
  }
  class XmlFragment {
    paragraph-per-line plain text
    hardBreak → newline
  }
  class YArray~PendingReviewRound~ {
    oldest first
  }
  class PendingReviewRound {
    id string
    operation EditOp or WriteOp
    baseHash? string
    trigger string
    timestamp number
    kind tiny or big
    stepCount number
  }
  YDoc --> XmlFragment
  YDoc --> YArray~PendingReviewRound~
  YArray~PendingReviewRound~ --> PendingReviewRound

    Putting content and review metadata inside the same Y.Doc is deliberate: a single transact(..., AGENT_ORIGIN) can atomically update both, so the browser sees the diff and the review card in the same frame.

    ConstantValueWhy it matters
    FRAGMENT_NAME'default'XmlFragment key
    REVIEW_ARRAY_NAME'rounds'Y.Array key
    AGENT_ORIGIN'agent'UndoManager tracks this
    USER_ORIGIN'user'Default for keystrokes
    SYSTEM_ORIGIN'system'Cold start / seed
    Origin strings must agree across boundaries. Server sets the origin on transact; it streams to the browser as a Yjs origin string; the client Y.UndoManager matches by string equality. Rename one side and review/undo silently breaks.
    06 Source of truth

    Three layers, one truth

    flowchart LR
  LiveDoc["Live Hocuspocus Y.Doc
    SOURCE OF TRUTH
    in-memory"]
  SQLite[("SQLite
    yjs_updates append log")]
  MD["workspace/*.md
    debounced 1s flush"]

  LiveDoc -- "onChange, per update" --> SQLite
  LiveDoc -- "500ms flush tick" --> MD
  SQLite -- "replayUpdatesInto on cold start" --> LiveDoc
  MD -- "seed on first-ever load" --> LiveDoc
    1. Live Y.Doc (in Hocuspocus memory) — authoritative while the process is alive.
    2. .docwriter/docwriter.db — durable. Every Yjs update is one row tagged with its origin. Server restart replays this log.
    3. <tab>.md on disk — plain markdown. Debounced backup for git and portability, not the source of truth. External edits are detected by mtime and folded in on cold start.

    This ordering is important: the DB is the durable store, not the markdown file. If you hand‑edit a file while the server is running, you won't lose data — but the live Y.Doc is still what the browser sees until the next cold start (or until --watch triggers a reload).

    07 On-disk shape

    The SQLite schema

    Everything the server needs to remember across restarts lives here. Defined in src/lib/server/db-schema.ts, migrated via PRAGMA user_version.

    CREATE TABLE yjs_updates (
  tab_id   TEXT NOT NULL,
  seq      INTEGER PRIMARY KEY AUTOINCREMENT,
  "update" BLOB NOT NULL,           -- reserved word; MUST be quoted
  origin   TEXT NOT NULL,           -- 'agent' | 'user' | 'system'
  created  INTEGER NOT NULL
);
CREATE INDEX yjs_updates_tab_id ON yjs_updates(tab_id);

CREATE TABLE tabs (tab_id PK, order_index, is_active);
CREATE TABLE rules (id PK, text, created_at);
CREATE TABLE hooks (id PK, event, matcher, command, enabled);
CREATE TABLE recent_actions (label, used_at);
CREATE TABLE action_usage_counts (action PK, count);
CREATE TABLE kv (key PK, value);

    KV keys currently in use:

    • sessionId — SDK session UUID for conversation resume
    • agentSettings — JSON: { agency, trackChanges }
    • editorSoftWrap — 'true' / 'false'
    • last_seen:<tabId> — markdown snapshot, used to build the diff the agent sees on the next render
    SQLite gotcha: update is a reserved word. Every SELECT / INSERT on that column must quote it as "update". Some builds silently ignore the missing quotes, others corrupt.
    08 Flow 1 of 6

    Flow: user keystroke → disk

    The simplest path. You type; the CRDT appends; SQLite persists; the markdown flushes.

    sequenceDiagram
  actor User
  participant TT as Tiptap (browser)
  participant HP as HocuspocusProvider
  participant H as Hocuspocus server
  participant P as ydoc-persistence.ts
  participant DB as SQLite
  participant FS as disk

  User->>TT: types a character
  TT->>HP: ySyncPlugin turns it into a Yjs update
  HP->>H: WebSocket update
  H->>H: apply to Y.Doc (origin = USER_ORIGIN)
  H->>P: onChange(update, origin)
  P->>DB: INSERT INTO yjs_updates (origin='user')
  P->>P: markTabDirty(tabId)
  H-->>HP: broadcast to other clients
  Note over P,FS: global 500ms flush tick
  P->>FS: atomic writeFile(tab.md)

    Two side effects worth knowing:

    • The browser serializes the editor to markdown locally and publishes to the userMd store — that's what feeds the outline.
    • The editor restarts a 3‑second idle timer (IDLE_MS = 3000). When it hits zero, auto‑submit fires a render. Cmd/Ctrl+Enter skips the wait.

    Key files: src/lib/server/ws-server.ts (onChange plumbing), src/lib/server/ydoc-persistence.ts (append + flush loop).

    09 Flow 2 of 6 — the most important one

    Flow: agent edit

    An agent tool call has to land content change and review card atomically. Here's how.

    sequenceDiagram
  participant SDK as Agent SDK
    (query loop)
  participant MCP as mcp-doc-tools.ts
  participant PR as path-router.ts
  participant H as Hocuspocus
  participant DC as DirectConnection
  participant DB as SQLite
  participant Br as Browsers

  SDK->>MCP: edit_doc(path, old, new)
  MCP->>PR: resolveTabFromPath(path)
  alt scratch path
    MCP->>MCP: plain filesystem edit
  else open tab
    MCP->>H: openDirectConnection(tabId)
    H-->>MCP: DirectConnection
    MCP->>DC: direct.transact(doc => ...)
    Note over DC: one doc.transact(..., AGENT_ORIGIN):
    1. serialize current, find unique old_string
    2. replaceYDocText(ydoc, newMd)
    3. reviewArray.push(PendingReviewRound)
    DC-->>H: Yjs update(s) origin=AGENT_ORIGIN
    H->>DB: append row origin='agent'
    H-->>Br: broadcast
    Br->>Br: Tiptap renders diff overlay
    + OutlinePane review card
  else unknown path
    MCP-->>SDK: isError: true
  end

    Three MCP tools, all in src/lib/server/mcp-doc-tools.ts:

    ToolPurposeFails when
    read_docSerialize the live Y.Doc (what the user actually sees now, including pending rounds).Unknown path.
    edit_docReplace exactly one occurrence of old_string.0 or >1 hits — agent must read_doc and retry with more context.
    write_docReplace the whole doc. Records a baseHash so if the user edits between propose and accept, the round is marked stale.Unknown path. Does not auto‑create tabs.
    Why not the built‑in Edit/Write? Those operate on files on disk, bypassing the live Y.Doc. DocWriter's authority is the live doc, so tools must edit what the browser is showing, not the debounced‑backup file. canUseTool in /api/render explicitly denies Read/Glob/Grep/Bash on open‑tab paths.
    10 Agent tool dispatch

    Path routing

    Before any work happens, each tool call is classified by its path argument. Three buckets, one source: src/lib/server/path-router.ts.

    flowchart TD
  path["path input"]
  path --> isScratch{"under
    .docwriter/agent/scratch/ ?"}
  isScratch -- yes --> scratchIO["plain filesystem I/O
    (agent private workspace)"]
  isScratch -- no --> matchTab{"matches entry in
    tabs.order ?"}
  matchTab -- "exact id" --> liveTab["open tab → live Y.Doc"]
  matchTab -- "absolute path suffix" --> liveTab
  matchTab -- no --> reject["isError: true
    write_doc never auto-creates tabs"]

    The scratch directory is the agent's private filesystem workspace at .docwriter/agent/scratch/. It's lazy‑created on first scratch write, and wiped on "New session." The agent uses it for research notes, outlines, and drafts that shouldn't appear as user tabs.

    11 Flow 3 of 6

    Flow: accept / reject review rounds

    Review rounds live inside Y.Array('rounds') on the Y.Doc itself. Accept/reject is just a Yjs mutation that propagates to every client.

    sequenceDiagram
  actor User
  participant UI as OutlinePane
  participant API as /api/tabs
  participant WS as ws-server.ts
  participant H as Hocuspocus Y.Doc
  participant UM as Y.UndoManager

  User->>UI: clicks Accept on round #k
  UI->>API: POST accept {tabId, roundId}
  API->>WS: acceptTabRounds(tabId, roundId?)
  WS->>H: openDirectConnection → transact:
    delete rounds[0..=k] from 'rounds'
  Note right of H: content stays put.
    round entries removed.
  H-->>UI: broadcast update

  User->>UI: clicks Reject on round #k
  UI->>API: POST reject {tabId, roundId}
  API->>WS: rejectTabRounds(tabId, roundId?)
  WS->>UM: undoManager.undo() × stepCount
  Note right of UM: UndoManager only tracks AGENT_ORIGIN,
    so user keystrokes survive.
  UM->>H: inverse transaction (origin='agent')
  H-->>UI: broadcast update

    The Y.UndoManager lives on the server, attached to each Y.Doc with trackedOrigins: new Set([AGENT_ORIGIN]) and captureTimeout: 0 (so each tool call is one undo step).

    Construction order matters. The UndoManager must be attached before replayUpdatesInto() runs. Otherwise, after a server restart, Reject on a round from a prior session becomes a no‑op because the undo stack is empty. See ws-server.ts for the guarded order.
    12 When a round can't apply

    Stale review rounds

    Between when the agent proposes an edit and when you accept it, you might edit the doc. That can make the proposal no longer make sense. DocWriter detects this and marks the round stale.

    Round kindHow staleness is detected
    edit_doc If old_string no longer appears exactly once in the current text, the round is stale. Either the user changed the match site, or the match is now ambiguous.
    write_doc Records baseHash = reviewTextHash(textAtProposal). If the current text's hash differs, the round is stale — the user has diverged from the base the agent rewrote.

    Stale rounds show up in materializePendingReviewRounds (src/lib/review-rounds.ts) with a staleReason. The UI disables Accept and tells you why.

    The mental model: proposals are advisory until accepted. Yjs handles structural convergence for you (two cursors editing at once never corrupts the doc). Staleness handles semantic conflict (the agent's proposal no longer fits).
    13 Flow 4 of 6 — the core agent loop

    Flow: the render loop (/api/render)

    One POST to /api/render = one invocation of the Claude Agent SDK's query(). The response is an SSE stream that drives the HistoryPane in real time.

    sequenceDiagram
  participant Br as Browser
  participant R as /api/render
  participant SDK as Agent SDK
  participant MCP2 as docwriter-doc MCP
  participant H as Hocuspocus
  participant DB as SQLite

  Br->>R: POST {userMessage?, model?, warmup?, planMode?}
  R->>R: buildSystemPrompt() (cached)
  R->>R: buildMultiTabPrompt(activeTab, tabs, userMessage)
  R->>SDK: query({ prompt, mcpServers, hooks, canUseTool })
  loop streaming events
    SDK-->>R: system / tool_call_start / tool_use / assistant_text / thinking / result
    R-->>Br: SSE event
    alt edit_doc / write_doc / read_doc
      SDK->>MCP2: tool call
      MCP2->>H: DirectConnection.transact(AGENT_ORIGIN)
      H-->>Br: Yjs update via WebSocket
    (parallel to SSE)
    else ExitPlanMode
      R-->>Br: plan_proposed; abort
    else AskUserQuestion
      R->>R: registerPendingAskUser(id, resolve, 15min)
      R-->>Br: user_question event
      Br->>R: POST /api/ask-user-reply {id, answers}
      R-->>SDK: resolve → agent continues
    else propose_rule / propose_hook
      R-->>Br: rule_proposal / hook_proposal
    end
  end
  R->>DB: kv['last_seen:'] = current markdown (per tab)
  R-->>Br: result + done
    Two channels, one render. Content arrives over the WebSocket (Yjs). Narration (tool calls, thinking summaries, status, proposals) arrives over the SSE stream. The SSE result event no longer carries markdown — the browser already has it.
    14 Feeding the agent

    Prompt construction

    buildMultiTabPrompt() in /api/render assembles the per‑render prompt. The strategy is to give the agent only what it needs to know what changed, and let it call read_doc if it wants more.

    Tab stateWhat we inline
    Active tabFull current content + unified‑line diff vs kv['last_seen:<tabId>'].
    Non‑active tab, changed since last renderPath + diff. Agent calls read_doc if it needs more.
    Non‑active tab, unchangedPath only.
    First‑render tab (no last_seen)Full content.

    Plus, appended to every prompt:

    • Persistent writing rules (from SQLite).
    • Agency guidance: one of three blocks based on agentSettings.agency (conservative / balanced / aggressive).
    • Style references block (see server/references.ts).

    After the render completes, last_seen:<tabId> is refreshed to the current markdown for every tab the agent saw. Next render diffs against what the agent knew last time.

    15 Read-only render variants

    Plan mode & warmup

    The same render endpoint supports two read‑only variants, implemented by narrowing what canUseTool allows.

    ModeWhat's allowedWhat's blocked
    planMode: true Reads, searches, read_doc All mutations (edit_doc, write_doc, Edit, Write, Bash). SDK fires ExitPlanMode → plan_proposed SSE event → user approves or rejects.
    warmup: true Only read/search + WebSearch / WebFetch Everything else — used to pre‑populate context with zero side‑effect risk.

    If the user approves a plan, the client re‑runs the render without planMode, and the agent executes the plan it just outlined.

    16 Flow 5 of 6

    Flow: AskUserQuestion

    When the agent needs to ask you something, the tool call is intercepted, parked in memory, and surfaced as a card in the UI. Your answer is fed back through a separate endpoint.

    sequenceDiagram
  participant SDK
  participant R as /api/render
  participant ST as ask-user-state.ts
  participant Br as Browser
  participant API as /api/ask-user-reply

  SDK->>R: canUseTool(AskUserQuestion, { questions })
  R->>ST: registerPendingAskUser(id, resolve, 15min)
  R-->>Br: SSE user_question { id, questions }
  Br->>Br: render question card in OutlinePane
  actor U as User
  U->>Br: pick answers, submit
  Br->>API: POST {id, answers}
  API->>ST: resolvePendingAskUser(id, answers)
  ST-->>R: promise resolves
  R-->>SDK: canUseTool returns { allow: true, input: { answers } }

    The parking state is in‑process memory (src/lib/server/ask-user-state.ts). If the server dies, pending questions time out after 15 minutes and the render aborts.

    propose_rule and propose_hook use a similar pattern (SSE event → UI card) but don't block the agent — they're fire‑and‑forget suggestions the user reviews later.

    17 Flow 6 of 6

    Flow: cold start & server restart

    When a browser first connects to a tab, Hocuspocus has to rebuild the Y.Doc from scratch. Here's the exact sequence:

    sequenceDiagram
  participant WS as ws-server.ts
  participant P as ydoc-persistence.ts
  participant DB as SQLite
  participant FS as disk
  actor Br as Browser

  Br->>WS: WS connect /
  WS->>WS: onLoadDocument(tabId): create Y.Doc
  WS->>WS: attach Y.UndoManager
    (trackedOrigins = {AGENT_ORIGIN})
    BEFORE replay
  WS->>P: replayUpdatesInto(ydoc, tabId)
  P->>DB: SELECT * FROM yjs_updates WHERE tab_id=? ORDER BY seq
  alt rows exist
    loop per row
      P->>P: ydoc.transact(
      () => applyUpdate(ydoc, row.update),
      row.origin
    )
      Note right of P: UndoManager observes each
    AGENT_ORIGIN transaction
    → stack restored
    end
    P->>FS: stat tab file
    alt mtime > last row + 2s skew
      Note over P,FS: external edit detected.
    reset doc from disk, compact log.
    end
  else no rows
    P->>FS: read <tabId> markdown
    P->>P: seedYDoc(ydoc, content) under SYSTEM_ORIGIN
    P->>DB: persist one compacted row
  end
  WS-->>Br: synced event
  Br->>Br: Tiptap mounts

    Two things to notice:

    • Replay preserves origins. That's what lets the UndoManager rebuild the agent‑undo stack across restarts. Without this, Reject on yesterday's round silently does nothing.
    • External edits are detected, not ignored. If you hand‑edited the file while the server was off, the mtime vs last‑row‑time check catches it, re‑seeds from disk, and compacts the log.

    The client Y.Doc registry (src/lib/yjs-doc.ts) keeps a { ydoc, wsProvider, readyPromise } per tab id. Tiptap doesn't mount until whenYDocReady() resolves, so there's never a flicker of unhydrated content.

    Server instance reconciliation. The server stamps a UUID on boot. If the browser's stored instance id doesn't match on reconnect, all client Y.Docs are reset and providers reconnect fresh — the server may have lost state and we don't want a stale client overwriting it.

    20 Inside TiptapEditor.svelte

    Editor update loop

    On every ProseMirror transaction, the editor runs this logic:

    1. If the transaction carries ySyncPluginKey meta (Yjs pushing a remote update into the editor), skip — no idle timer, no serialization side effects. This is how Yjs updates come in without being mistaken for user typing.
    2. Otherwise, serialize the editor content to markdown and publish it to the userMd store (that's what the outline reads).
    3. If the transaction carries AGENT_APPLY_KEY meta (set locally when an agent‑origin Y.Doc update is applied), skip the idle‑timer restart. An agent edit isn't "the user is still writing."
    4. Otherwise, restart the 3‑second idle‑submit countdown.

    Cmd/Ctrl+Enter skips the countdown and submits immediately. The client does not PUT /api/document with markdown — the server's Y.Doc‑to‑disk flush owns that entirely.

    Origin matching gotcha. AGENT_ORIGIN on the server and AGENT_APPLY_KEY on the client are separate concepts but related: the server tags transactions with the origin string; the client's editor‑update handler uses the apply‑key meta to decide whether to restart the idle timer. Don't rename one without the other.
    21 What the browser talks to

    API surface

    All under src/routes/api/. Most are thin — the exception is render, which is where the agent loop lives.

    EndpointPurpose
    render/SSE stream. POST kicks off one Agent SDK query(). Returns tool events, thinking, proposals, status. The core agent loop.
    tabs/GET order/active/tabs. POST opens/creates. PATCH focuses or renames. DELETE closes, optionally deletes file. Also hosts accept/reject review endpoints.
    document/GET reads workspace file + metadata (calls flushTabMarkdownNow first). PUT accepts only meta (rules / agent settings). Accept/reject are Y.Map mutations, not here.
    files/Workspace file tree: list / create / rename / move / delete.
    file-content/Raw read/write for non-editor files.

    24 Things that have burned us

    Gotchas you'll probably hit

    Origin strings must agree. Server sets the origin on transact; it streams to the browser as a string; the client matches by string equality. Rename one side and UndoManager/review silently breaks.
    UndoManager attach‑before‑replay. Construct the Y.UndoManager before replayUpdatesInto. Otherwise cold start leaves the undo stack empty and Reject becomes a no‑op for rounds from prior sessions.
    Hocuspocus's internal Document is authoritative. Once a client has connected and onLoadDocument has run, Hocuspocus's own Document is the source of truth. Server code mutating a tab must go through server.hocuspocus.openDirectConnection(tabId) — not a cached Y.Doc reference.
    "update" is a SQLite reserved word. Always quote the column. Unquoted works silently on some builds, corrupts on others.
    Tiptap‑markdown escapes brackets. The serializer turns [ into \[. read_doc returns the escaped form, and edit_doc's old_string must match. If an edit fails with "not found" in a spot you can see, check bracket escaping.
    undoRedo: false in StarterKit. Collaboration ships its own Yjs undo. Registering both corrupts plugin state.
    Link is bundled via StarterKit. Don't import @tiptap/extension-link separately.
    Vite HMR re‑executes hooks.server.ts. The globalThis.__docwriterWsServer guard keeps us from double‑binding the WS port on every save.
    25 The why

    Design principles

    When you're making a call that the doc doesn't cover, these are the tiebreakers.

    1. User edits must not be lost. Per‑tab Y.Docs, AGENT_ORIGIN isolation for undo, CRDT item‑level merge for concurrent writes.
    2. Agent work must remain reviewable. Every edit_doc / write_doc atomically pairs its content change with a PendingReviewRound.
    3. The app works against a real folder, not a sandbox. Workspace‑relative tab ids, filesystem‑backed APIs, file tree + raw file endpoints, CLI root selection.
    4. Single source of truth. The live Hocuspocus Y.Doc owns editor content; SQLite owns the Yjs update log; markdown on disk is a debounced backup. No IndexedDB, no shadow files, no 3‑way merge.
    5. Origin tagging over explicit reconciliation. All mutation flows through Yjs with an origin string. Review, undo, history all drop out of that log.
    26 Takeaway

    Bottom line

    DocWriter is a local multi‑file writing environment where:

    • each tab is a server‑owned CRDT synced to the browser over WebSocket,
    • every Yjs update is appended to a SQLite log tagged with its origin,
    • a Claude Agent SDK loop edits the live Y.Doc through custom MCP tools (atomic content + review card, no shadows, no merge),
    • review queue entries are just items in a Y.Array inside the same doc,
    • markdown on disk is a debounced backup for git and portability.

    Content convergence is the CRDT's job. Everything else — review, undo, reject, history — is a consequence of origin‑tagged transactions on a single authoritative doc.
