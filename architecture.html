    01 Start here

    What is DocWriter?

    DocWriter is a local markdown editor with an AI writing partner. You type; an AI agent can also propose edits to the same document. You see its suggestions as review cards you accept or reject, the way you'd review tracked changes in Word.

    That's the product. The interesting part — and what this walkthrough is about — is how two writers (you and an AI) edit the same document at the same time without stepping on each other, while keeping every agent change reviewable.

    This walkthrough assumes you know TypeScript and have written a web app, but not that you know any of the specific libraries below. Hit → (or Space) to advance. The TOC on the left lets you jump around.

    Vocabulary — the names you'll see repeated.
    • Tiptap — the rich‑text editor component that runs in the browser. Like a fancier <textarea>. Built on ProseMirror.
    • Yjs — a library for a data structure called a CRDT. Think of it as a document that multiple people can edit simultaneously; Yjs guarantees every participant converges to the same final text, no matter what order the keystrokes arrive in. This is the same idea behind Google Docs. A Yjs document is called a Y.Doc.
    • Hocuspocus — a server for Yjs. It holds a Y.Doc in memory, accepts WebSocket connections from clients, and relays every change to every connected client.
    • Origin — a label attached to each edit saying who made it. Yjs lets you tag transactions with an arbitrary origin string and see that tag when the change is applied. DocWriter uses three: 'user' for your keystrokes, 'agent' for edits the AI makes, and 'system' for changes the server itself produces — specifically, the one-time seeding of a fresh Y.Doc from the markdown file on disk when a tab is opened for the first time. Tagging that seed as 'system' (not 'user') keeps it out of your undo history, and (not 'agent') keeps it out of the AI's review log.
    • MCP (Model Context Protocol) — the way the AI agent calls tools. An "MCP tool" is a function the agent can invoke. DocWriter exposes tools like edit_doc that the agent calls to modify the document.
    • SSE (Server‑Sent Events) — a one‑way stream from server to browser over HTTP. We use it to stream the agent's thinking and tool calls into the UI in real time.

    02 Core invariant

    The one big idea

    Here's the problem we need to solve. Two writers — you and the AI — need to edit the same document at the same time. And every edit the AI makes needs to appear as a reviewable suggestion you can accept or reject, without freezing the document while you think about it.

    A naive design would give the AI its own copy of the file, let it edit there, then try to merge its changes back into yours later. That's a 3‑way merge (your version, the AI's version, their common ancestor) and it's the kind of thing that makes git conflicts painful. We don't want to build that.

    The trick: there is only one copy of the document, and it lives on the server. Both you and the AI are clients connecting to it. Every change — yours or the AI's — is a tagged transaction on that one shared document.

    • Each tab's document is a Y.Doc held by the Hocuspocus server in memory. It's the single authoritative copy.
    • Your browser connects over a WebSocket. Your keystrokes are sent as Yjs transactions tagged with origin 'user'.
    • The AI agent connects in‑process (same Node server, no network hop) and sends its edits as Yjs transactions tagged with origin 'agent'.
    • Yjs guarantees everyone converges to the same text. Concretely: every character inserted into a Y.Doc is assigned a stable identifier (client id + clock tick), and its position is stored relative to its neighbors' ids, not as a numeric offset. So if you type at the start while the agent inserts at the end, the two updates describe operations on different identified positions — applying them in either order produces the same final sequence, byte for byte. No diff3, no merge conflicts, no "whose change wins." The tradeoff is that reads require walking this linked structure, but Yjs keeps that fast in practice.
    • Every transaction is appended to a SQLite log with its origin tag, then broadcast to every connected client.

    Once you have this, everything else falls out for free:

    • Review / undo / reject an AI edit — we can filter the log by origin = 'agent' and replay only those transactions backwards.
    • "What did the agent just do?" — read the entries in the log since the render started, in order.
    • Show review cards — the AI's tool call writes both the content change and a "please review this" entry in one atomic transaction, so they always appear together.

    That's the whole architecture, compressed. The rest of this walkthrough is details.

    03 What runs where

    Processes and ports

    When you run docwriter in a workspace, one Node process starts and hosts two servers on different ports:

    • SvelteKit HTTP on PORT — renders the page, hosts /api/* endpoints.
    • Hocuspocus WebSocket on DOCWRITER_WS_PORT (default 3001) — the Y.Doc sync channel.

    The Agent SDK loop is spawned per render inside that same process — it's not a separate service. It talks to Hocuspocus through an in‑process DirectConnection, not the WebSocket.

    A dev‑mode gotcha worth knowing. In dev, Vite uses Hot Module Replacement (HMR): when you save a file, it re‑executes just the changed module instead of restarting the whole server. That's usually great, but hooks.server.ts is where we start the Hocuspocus WebSocket server, and if that code re‑runs on every save, the second run tries to bind port 3001 while the first one is still holding it — crash. The fix is to stash the running server on globalThis.__docwriterWsServer. On re‑execution, we check whether the global is already set; if so, we reuse the existing server instead of starting a new one. globalThis survives module re‑execution because it's on the Node runtime, not the module.

    05 Data model

    What's inside a Y.Doc

    Before reading the diagram, it helps to know what's Yjs's vocabulary and what's ours:

    • From Yjs (built in): Y.Doc (the document container), Y.XmlFragment (a shared type for tree-structured rich text — Tiptap/ProseMirror binds to it), Y.Array (a shared list), Y.Map (a shared dictionary). Yjs gives you these primitives; the CRDT merge math lives inside them.
    • Our choices: putting exactly one XmlFragment (under the key 'default') and one Y.Array (under the key 'rounds') inside every tab's Y.Doc; the shape of each PendingReviewRound entry; and the rule that content + review metadata live in the same doc so they update atomically. Defined once in src/lib/shared/ydoc-codec.ts and reused by server and client so the schema can never drift.

    So in the diagram below: the orange card is a Yjs primitive, the blue cards are Yjs primitives used with keys and conventions we defined, and the nested PendingReviewRound is purely our shape.

    Putting content and review metadata inside the same Y.Doc is deliberate: a single transact(..., AGENT_ORIGIN) can atomically update both, so the browser sees the diff and the review card in the same frame.

    ConstantValueWhy it matters

    Origin strings must agree across boundaries. Server sets the origin on transact; it streams to the browser as a Yjs origin string; the client Y.UndoManager matches by string equality. Rename one side and review/undo silently breaks.
    06 Source of truth

    Three layers, one truth

    The document exists in three places at once. Only one of them is authoritative at any given moment. The other two are derived views, kept up to date so we can survive restarts and play nicely with git.

    1
    Live Y.Doc in Hocuspocus memory
    source of truth, while the server is running

    This is the actual object the browser edits and the agent edits. When the server is up, this is what everyone reads from and writes to. If it disagrees with the other two layers, it wins.

    ↓
    On every Yjs update — append one row to yjs_updates, tagged with its origin (user / agent / system). Synchronous, so a crash mid-edit loses at most the in-flight update.
    On server cold start — replay every row for this tab, in order, back into a fresh Y.Doc. The origins replay too, so the agent-undo stack is restored.
    ↑
    2
    .docwriter/docwriter.db — SQLite append log
    durable, survives restarts

    A table called yjs_updates: one row per Yjs transaction, ever. This is what makes the live doc recoverable after the process dies. It's not designed for humans to read — it's a binary log of CRDT operations.

    ↓
    Every ~1s, if dirty — serialize the live doc back to text and atomically overwrite the tab's file at its original path (drafts/chapter-1.md, notes.txt, script.py — whatever the user named it). "Serialize" here just means walking the XmlFragment and joining paragraphs with \n; DocWriter doesn't reformat or interpret the content. Debounced so we don't thrash the disk on every keystroke.
    First-ever load of a tab (no rows in the DB yet) — read the file at the tab's path (whatever extension it has), seed the Y.Doc with its contents, and tag the seed with origin 'system'.
    ↑
    3
    The tab's file on disk — at its original path and extension
    backup, for git and portability

    This is the file the user actually owns: chapter-1.md, notes.txt, script.py, whatever they named it. It's what you see if you open the file in another editor, diff it in git, or copy it elsewhere. It's rewritten from the live doc on a debounced tick, so it lags the live doc by up to ~1s. External edits (while the server is off, or via --watch) are detected by comparing the file's mtime to the timestamp of the last row in the log.

    Why this ordering matters. If you hand-edit a markdown file while the server is running, you won't lose data — the edit stays on disk. But the live Y.Doc is still what the browser sees, so your change won't show up until the next cold start (or a --watch-triggered reload). The DB is the durable store; the markdown file is a derived artifact.
    07 On-disk shape

    The SQLite schema

    Everything the server needs to remember across restarts lives here. Defined in src/lib/server/db-schema.ts, migrated via PRAGMA user_version.

    CREATE TABLE yjs_updates (
  tab_id   TEXT NOT NULL,
  seq      INTEGER PRIMARY KEY AUTOINCREMENT,
  payload  BLOB NOT NULL,           -- the raw Yjs update bytes
  origin   TEXT NOT NULL,           -- 'agent' | 'user' | 'system'
  created  INTEGER NOT NULL
);
CREATE INDEX yjs_updates_tab_id ON yjs_updates(tab_id);

CREATE TABLE tabs (tab_id PK, order_index, is_active);
CREATE TABLE rules (id PK, text, created_at);
CREATE TABLE hooks (id PK, event, matcher, command, enabled);
CREATE TABLE recent_actions (label, used_at);
CREATE TABLE action_usage_counts (action PK, count);
CREATE TABLE kv (key PK, value);

    KV keys currently in use:

    • sessionId — SDK session UUID for conversation resume
    • agentSettings — JSON: { agency, trackChanges }
    • editorSoftWrap — 'true' / 'false'
    • last_seen:<tabId> — markdown snapshot, used to build the diff the agent sees on the next render

    The blob column is named payload. (Earlier versions of DocWriter named it update — a SQLite reserved word, which forced every SELECT/INSERT to quote it as "update" and silently corrupted data on builds that tolerated the missing quotes. Migration v2 renames it.)

    Flow: cold start & server restart

    When a browser first connects to a tab, Hocuspocus has to rebuild the Y.Doc from scratch. Here's the exact sequence:

    Two things to notice:

    • Replay preserves origins. That's what lets the UndoManager rebuild the agent‑undo stack across restarts. Without this, Reject on yesterday's round silently does nothing.
    • External edits are detected, not ignored. If you hand‑edited the file while the server was off, the mtime vs last‑row‑time check catches it, re‑seeds from disk, and compacts the log.

    Flow: user keystroke → disk

    The simplest path. You type; the CRDT appends; SQLite persists; the markdown flushes.

    Two side effects worth knowing:

    • The browser serializes the editor to markdown locally and publishes to the userMd store — that's what feeds the outline.

    10 Flow 2 of 5 — the most important one

    Flow: agent edit

    For any workspace file — whether it's currently an open tab or not — the agent uses three custom MCP tools (defined in src/lib/server/mcp-doc-tools.ts) instead of Claude's built-in Edit / Write. The built-ins operate on raw disk, which lags the live Y.Doc by up to a second and bypasses the review system entirely; canUseTool in /api/render denies them outside the agent's scratch directory. The custom tools edit the live Y.Doc directly, auto-open files as tabs when needed, and route through the review flow.

    The three tools, with their real signatures

    read_doc
    read_doc({
  path: string   // tab id (e.g. "drafts/chapter-1.md") or absolute
                 // path to an open tab, or a path under
                 // .docwriter/agent/scratch/
}) → string

    Returns the current text the user is looking at, including any pending review proposal on top of the committed content. Fails if path isn't an open tab or a scratch file.

    edit_doc
    edit_doc({
  path: string,
  old_string: string,       // must appear at least once
  new_string: string,       // can be empty (i.e. delete the match)
  replace_all?: boolean     // default false; see below
}) → "Edit applied to <path>."
  // or: "Edit applied to <path> (replaced N occurrences)."

    Replaces old_string with new_string. If the path points to a workspace file that isn't currently an open tab, edit_doc auto-opens it as a tab first. The edit lands as a pending review proposal — the committed document doesn't change until the user clicks Accept. By default old_string must match exactly once (so the review card shows one clearly-contextualized hunk); the tool fails with an informative message on zero or >1 matches. Pass replace_all: true to replace every occurrence as a single atomic proposal, useful for renames or consistent term updates. Fails if the file doesn't exist — use write_doc to create new files.

    write_doc
    write_doc({
  path: string,    // workspace path; may be a brand-new file
  content: string  // the full new contents
}) → "Wrote <N> chars to <path>."
  // or: "Created <path> (<N> chars) and opened as a new tab."

    Replaces the entire content. Three cases:

    • Path exists on disk, tab already open — proposes a pending review round. Stashes a baseHash so if the user edits before accepting, the round is marked stale.
    • Path exists on disk, tab not open — auto-opens it as a tab, then proposes the pending review round (same as above).
    • Path does not exist — creates the file with the given content and opens it as a new tab. No review round: there's nothing to compare against, so the content commits immediately as the file's initial state.
    How to pick. Change one specific spot → edit_doc with a unique old_string. Rename a term or fix a typo appearing in many places → edit_doc with replace_all: true. Rewriting most of an existing file → write_doc. Creating a brand-new draft → write_doc with a path that doesn't exist yet.
    Built-in Edit / Write are restricted to the scratch directory. canUseTool in /api/render denies any built-in Edit or Write whose target isn't under .docwriter/agent/scratch/. That keeps workspace writes on the reviewable path — the agent literally cannot edit a user-facing file without going through edit_doc / write_doc. Built-in Read / Glob / Grep remain unrestricted across the workspace (except that reading an open-tab file through Read is redirected to read_doc so the agent sees the review-aware content).

    What happens when edit_doc is called on an open tab

    1. 1
      Path classification

      The tool checks the path. Three possibilities: under .docwriter/agent/scratch/ (plain filesystem edit, no Yjs, no review card), matches an open tab (continue below), or unknown (returns isError: true).

    2. 2
      Open a DirectConnection to the live Y.Doc

      Calls hocuspocus.openDirectConnection(tabId). This is an in-process connection — no network hop, no WebSocket. But it goes through Hocuspocus's normal document-resolution, so we're operating on the same Y.Doc that every connected browser is synced to.

    3. 3
      One atomic transaction with origin = AGENT_ORIGIN

      Inside direct.transact(doc => { ... }) we do three things in sequence: serialize the current document to find the old_string match (fail out if 0 or >1 matches), rebuild the XmlFragment from the new text, and push a new PendingReviewRound onto the Y.Array. Because it's one transaction, Yjs emits one combined update — the content change and the review entry always arrive together.

    4. 4
      Hocuspocus does the rest

      The transaction fires Hocuspocus's onChange, which appends one row to yjs_updates with origin = 'agent', then broadcasts the update over WebSocket to every connected browser. The browser receives it like any other remote update — Tiptap renders the diff overlay, the outline shows a new review card. No special client-side agent code is needed.

    12 Flow 3 of 5

    Flow: accept / reject review rounds

    Review rounds live inside Y.Array('rounds') on the Y.Doc itself. Accept and Reject are just Yjs mutations on that array (and on the content fragment), broadcast to every connected client like any other edit.

    ✓ Accept
    1. User clicks Accept on round k in the outline.
    2. Browser → POST /api/tabs with { tabId, roundId }.
    3. The server opens a DirectConnection to the live Y.Doc and in one transaction deletes rounds 0…k from the Y.Array('rounds').
    4. The content doesn't change. The pending proposal was already materialized into the live text when the round was created; accepting just removes the "please review" entry from the queue.
    5. Hocuspocus broadcasts the array-mutation update; every browser re-renders with the card gone.
    ✗ Reject
    1. User clicks Reject on round k.
    2. Browser → POST /api/tabs with { tabId, roundId }.
    3. The server calls undoManager.undo() stepCount times — where stepCount is the number of undo-stack entries that round pushed when it was proposed.
    4. Because the UndoManager is configured with trackedOrigins: new Set([AGENT_ORIGIN]), undo() rolls back only the agent's edits; any user keystrokes that landed in between are left intact.
    5. The inverse transaction itself fires with origin = 'agent', so Hocuspocus broadcasts it to everyone just like the original edit.

    How does Reject actually undo the agent's change? With a Y.UndoManager — a Yjs helper that watches a Y.Doc and maintains a stack of inverse operations. You configure it with trackedOrigins: new Set([AGENT_ORIGIN]), which means "only record transactions whose origin tag matches 'agent'." User keystrokes land with origin 'user' and are ignored; agent edits land with origin 'agent' and get pushed onto the stack. Calling undoManager.undo() then pops the top entry and applies its inverse — rolling back exactly one agent edit while leaving every user keystroke that happened in between untouched. The captureTimeout: 0 setting means "don't coalesce consecutive agent edits into a single undo step" — each tool call is one discrete entry on the stack.

    Why the server has to build the UndoManager before it replays the update log. On cold start, the server reconstructs each tab's Y.Doc by reading the yjs_updates table in order and calling ydoc.transact(() => applyUpdate(ydoc, row.payload), row.origin) once per row. Each of those transactions fires through every observer currently attached to the doc, including the UndoManager's. The UndoManager only records transactions that happen after it's attached — if you build it after the replay loop, every historical agent edit slips past it unseen, and the undo stack starts empty. That means Reject on yesterday's pending review round silently does nothing: there's no stack entry to pop. Swap the order and Reject works across restarts. The guarded order lives in ws-server.ts: construct the UndoManager first, then call replayUpdatesInto(), so the replay transactions all flow through the observer with their original origins and the stack ends up exactly as it was before the restart.
    13 When a round can't apply

    Where conflicts can actually happen

    With two writers on one doc, there are three moments where they might collide. Yjs handles the first automatically; the other two we have to handle ourselves.

    1. User and agent typing at the same time

    This is the classic concurrent-editing case, and it's the one problem Yjs already solves. Both writers land transactions on the shared Y.Doc; the CRDT math merges them deterministically regardless of arrival order. There's no "conflict" to resolve — the final text contains both changes in a consistent order, and every client converges to the same bytes. Nothing to worry about here.

    2. Agent proposes an edit against stale text (edit-time)

    Between when the agent last read the doc and when its edit_doc transaction runs, the user might have typed. Could the agent's old_string match no longer exist?

    The agent always reads the live doc. edit_doc doesn't work from a cached copy — inside runTabWrite, it opens a DirectConnection, starts a transaction, and only then serializes the current text to find the old_string. The user's concurrent keystrokes have already landed. If the match fails now (zero or, without replace_all, more than one hit), the tool errors out with a clear message and the agent retries with a fresh read_doc. write_doc doesn't need a match check — it's whole-file.

    So at edit time: no silent failure. Either the tool lands its proposal atomically, or it tells the agent to try again.

    3. User edits between proposal and Accept (accept-time)

    This is where real semantic conflict lives. Say the agent proposes "replace dog with wolf in this sentence," and before you click Accept you edit that sentence to remove the word dog entirely. Structurally the doc is fine (Yjs merged your keystrokes with the agent's pending-round entry in Y.Array('rounds')). But semantically, applying the proposal now would do the wrong thing — or nothing, or the wrong place. That's what we call staleness.

    How staleness is detected at Accept time
    • edit_doc rounds — right before commit, applyPendingReviewRound re-counts old_string in the current text. Zero matches → stale ("the original text is no longer present"). Multiple matches (and replaceAll was false) → stale ("now matches multiple locations, ambiguous"). Exactly one match → proceed.
    • write_doc rounds — at proposal time we stash baseHash = reviewTextHash(textAtProposal). At Accept, we re-hash the current text and compare. Mismatch → stale ("the document changed after this full-document rewrite was proposed"). The baseHash lets us detect any divergence, including edits that happen to leave the text visually similar.

    What happens when you click Accept on a stale round

    The server's commit path (acceptTabRounds in ws-server.ts) re-runs the staleness check right before writing. If it's stale, it throws a StalePendingReviewError that includes the reason and the offending staleRoundId. The /api/document route surfaces that as an HTTP 409 with { stale: true, staleRoundId, error: reason }.

    The client catches the 409 and automatically does the sensible thing instead of showing a generic error: it drops the stale round (via the normal reject path) and re-submits to the agent with a structured follow-up that contains the original proposal diff, the reason it went stale, and an instruction to re-read the file and re-propose. The agent's next turn sees the current text (including your edits) and produces a fresh proposal that fits. You don't lose your intent — the "I wanted this change" signal rides the retry.

    This is the buildStaleAcceptFollowup path in src/routes/+page.svelte. A history entry ("Proposal was stale — re-queuing the agent with the current text") tells you why a retry fired.

    Can you manually retry the agent?

    Yes, any time. The automatic stale-retry above is just a convenience. Any new render — Wake-Up button, Cmd/Ctrl+Enter, or the 3-second idle auto-submit — calls /api/render fresh, which reads the current live doc (including your edits) as context. Rejecting a stale round first keeps the review queue clean; a fresh render then produces rounds that fit the text as it is now.

    The mental model in one line. Yjs handles structural convergence (two cursors editing simultaneously never corrupt the doc). We handle semantic conflict (a stale proposal shouldn't clobber the user's newer edit). Edit-time staleness is caught by the tool's match check; accept-time staleness is caught by the commit path's re-check and baseHash.
    14 Feeding the agent

    Prompt construction

    buildMultiTabPrompt() in /api/render assembles the per‑render prompt. The strategy is to give the agent only what it needs to know what changed, and let it call read_doc if it wants more.

    Tab stateWhat we inline
    Active tabFull current content + unified‑line diff vs kv['last_seen:<tabId>'].
    Non‑active tab, changed since last renderPath + diff. Agent calls read_doc if it needs more.
    Non‑active tab, unchangedPath only.
    First‑render tab (no last_seen)Full content.

    Plus, appended to every prompt:

    • Persistent writing rules (from SQLite).
    • Agency guidance: one of three blocks based on agentSettings.agency (conservative / balanced / aggressive).
    • Style references block (see server/references.ts).

    After the render completes, last_seen:<tabId> is refreshed to the current markdown for every tab the agent saw. Next render diffs against what the agent knew last time.

    15 Read-only render variants

    Plan mode & warmup

    The same render endpoint supports two read‑only variants, implemented by narrowing what canUseTool allows.

    ModeWhat's allowedWhat's blocked
    planMode: true Reads, searches, read_doc All mutations (edit_doc, write_doc, Edit, Write, Bash). SDK fires ExitPlanMode → plan_proposed SSE event → user approves or rejects.
    warmup: true Only read/search + WebSearch / WebFetch Everything else — used to pre‑populate context with zero side‑effect risk.

    If the user approves a plan, the client re‑runs the render without planMode, and the agent executes the plan it just outlined.

    16 Flow 4 of 5

    Flow: AskUserQuestion

    When the agent needs to ask you something, the tool call is intercepted, parked in memory, and surfaced as a card in the UI. Your answer is fed back through a separate endpoint.

    sequenceDiagram
  participant SDK
  participant R as /api/render
  participant ST as ask-user-state.ts
  participant Br as Browser
  participant API as /api/ask-user-reply

  SDK->>R: canUseTool(AskUserQuestion, { questions })
  R->>ST: registerPendingAskUser(id, resolve, 15min)
  R-->>Br: SSE user_question { id, questions }
  Br->>Br: render question card in OutlinePane
  actor U as User
  U->>Br: pick answers, submit
  Br->>API: POST {id, answers}
  API->>ST: resolvePendingAskUser(id, answers)
  ST-->>R: promise resolves
  R-->>SDK: canUseTool returns { allow: true, input: { answers } }
  SDK->>SDK: agent sees answers in tool_result, continues

    The parking state is in‑process memory (src/lib/server/ask-user-state.ts). If the server dies, pending questions time out after 15 minutes and the render aborts.

    propose_rule and propose_hook use a similar pattern (SSE event → UI card) but don't block the agent — they're fire‑and‑forget suggestions the user reviews later.
