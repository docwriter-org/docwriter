DocWriter · Engineering Overview

A local-first writing editor whose editor state lives on the server.

DocWriter edits real files in a real folder on disk. Each open tab is backed by a CRDT document (Y.Doc) whose authoritative copy lives on a Hocuspocus WebSocket server running in the same Node process as SvelteKit. The browser is a synced client. The agent edits tabs through custom MCP tools that transact directly against the live server document — no shadows, no post-hoc merge.

SvelteKit + Tiptap Server Y.Doc Hocuspocus WebSocket SQLite yjs_updates Claude Agent SDK Custom MCP tools Origin-tagged undo
Section 1

At a glance

One Node process, one folder. The server holds the authoritative Y.Doc per tab and persists every CRDT update into SQLite, origin-tagged. The browser connects a HocuspocusProvider per open tab and is always in sync. The agent mutates the same live document the browser is looking at, through custom MCP tools.

Core invariant

The server Y.Doc is the source of truth. Every change — user keystroke or agent edit — is a Yjs transaction with an explicit origin that appends to the yjs_updates log and broadcasts to every connected client. document.md is a debounced backup; it is never read back into the running system unless the tab is brand new and the update log is empty.

Section 2

Mental model: one Y.Doc, three places you can see it

Vocabulary (used everywhere below)
  • Render. One full agent cycle: the user pauses (or clicks Wake), the server calls the Claude Agent SDK once, the agent uses edit_doc/write_doc to mutate open tabs, the stream of events flows back to the browser. Begins when the user triggers it; ends when the SDK emits a final result.
  • Y.Doc. The per-tab CRDT. An XmlFragment named default holds the editor content; a Y.Map named review holds pending review rounds. Lives authoritatively on the server; browsers have live mirrors via HocuspocusProvider.
  • Origin. Every Yjs transaction carries a string tag. 'agent' for the custom MCP tools, defaults to 'user' for browser-driven updates, 'system' for cold-start seeding. The UndoManager tracks only 'agent' — that's the whole mechanism behind Reject.
  • Review round. One edit_doc/write_doc call produces one round: a PendingReviewRound entry appended to Y.Map('review').pendingRounds in the same transaction as the content change. Surfaced in the UI as a card with Accept / Reject.
  • DirectConnection. A Hocuspocus handle that lets server-side code transact against the live Document as if it were a client. The custom MCP tools use it; this is the only correct way for server code to mutate a tab once any browser has connected.

The one hard idea to hold: there is exactly one Y.Doc per tab, and it lives on the server. What you see in the browser is a synced copy. What you see on disk is a debounced serialization. Neither is the source of truth.

What changed from the old model

The previous architecture had three independent worlds — a browser Y.Doc, a disk file, and a filesystem shadow for the agent — held together by a 3-way merge at each agent apply. All three worlds are gone. There is now one Y.Doc, with a serialization (disk) and a mirror (browser). The CRDT handles convergence; no post-hoc merge is needed.

Section 3

What the user does

Before the code, picture an actual writing session. Every architectural decision earns its keep against this workflow.

  1. Launch against a folder. The user runs docwriter pointed at a workspace directory. The CLI sets DOCWRITER_ROOT, starts SvelteKit + Hocuspocus in one Node process, and opens the browser.
  2. Open a file. The file tree lists the workspace. Clicking a file opens it as a tab. The browser instantiates a fresh Y.Doc + HocuspocusProvider for that tab id; the server either replays the tab's yjs_updates log or, if it's empty, seeds from the on-disk file. The editor mounts once the provider reports synced.
  3. Write. Every keystroke updates the browser Y.Doc, which immediately streams the Yjs update to the server. One idle timer runs in the background, reset on every keystroke:
    • Idle-submit (3s): after a full 3 seconds of quiet, submit() runs and kicks off a render — the agent wakes up. Press Cmd/Ctrl + Enter to skip the wait.
    A second timer lives on the server: 1 second after the last Yjs update, the server serializes the current Y.Doc to markdown and writes document.md. Client no longer initiates disk writes.
  4. Agent wakes. The right-hand history pane streams the agent's thinking, tool calls, and progress live over SSE. The user can keep typing while this happens — the agent's edits and the user's keystrokes converge in the server Y.Doc via the CRDT.
  5. Review proposal. When the agent calls edit_doc, the content change and the review-round entry reach the browser in one atomic update. A card appears in the OutlinePane with Accept / Reject. The diff overlay renders against the stored beforeMd.
  6. Accept, reject, or keep writing. Accept removes the round from Y.Map('review'). Reject additionally calls undoManager.undo() to rewind the agent's transactions — user edits that landed in between are untouched (they're not in the tracked-origin set).

Section 5 · Data flow

Flow: the user types a character

Primer: Tiptap, ProseMirror, Yjs origins
  • ProseMirror is the low-level editor engine; Tiptap wraps it. DocWriter uses Tiptap + @tiptap/extension-collaboration, which binds a ProseMirror editor to a Y.XmlFragment. Editor edits translate to Yjs ops.
  • Yjs transactions carry an origin string. When the browser's ySyncPlugin translates a ProseMirror transaction into Yjs ops, it uses its own plugin key as the origin. Server-side DirectConnection.transact(..., 'agent') uses the string AGENT_ORIGIN. The UndoManager watches origin tags.
  • Three kinds of ProseMirror transactions reach the update handler:
    1. User keystrokes — local edits. Rebroadcast over WebSocket by Tiptap's Collaboration plugin.
    2. Remote updates — Yjs updates arriving via HocuspocusProvider (another client's keystroke, or the agent's edit). The ySyncPlugin marks these with ySyncPluginKey meta.
    3. Agent-origin apply — a remote update whose Yjs origin equals AGENT_ORIGIN. The editor tags the derived ProseMirror transaction with AGENT_APPLY_KEY meta so the update handler can recognize it.

The update handler in TiptapEditor.svelte is a short series of "is this X? then Y" checks. No autosave path; no disk write; no serialize-for-outline-only step.

  1. Tiptap fires onUpdate(transaction). Something just changed the document. We inspect the transaction's metas.
  2. If the transaction is a Yjs hydration, return early.

    Concretely: if (transaction.getMeta(ySyncPluginKey) !== undefined) return;. That marker fires while the ySyncPlugin catches up to a fresh Y.Doc state — for example, right after the synced event on page load. Touching userMd or triggering any side effects during hydration can desynchronize the editor.

  3. Serialize the editor content and publish to the userMd store. Markdown tabs run a markdown serializer; plain tabs emit raw text. Subscribers to userMd (outline pane, diff overlay, some UI projections) re-render.

    The store does not drive disk writes — the server owns the markdown flush. userMd is a pure convenience projection so reactive UI code doesn't each re-serialize the Y.Doc.

  4. If the transaction carries AGENT_APPLY_KEY, stop here.

    The update came from the WebSocket with Yjs origin 'agent'. It's a valid document change, but not "the user is writing," so we don't restart the 3-second idle timer. (If we did, every agent edit would reset the auto-submit clock and the agent would never fire again.)

  5. Restart the 3-second idle-submit countdown. Clear any existing idle timer, start a new one. On timeout, submit() kicks off a render. Cmd/Ctrl + Enter fires it immediately.

On the server side (same keystroke, parallel track)

While the local editor reacts, the browser's Collaboration plugin has already encoded the change as a Yjs update and sent it over the WebSocket. Server-side:

  1. Hocuspocus receives the update. It applies to the tab's internal Document, advancing the authoritative state. Fires onChange.
  2. onChange appends to yjs_updates. transactionOrigin here is a Connection object (not a string), so we default the recorded origin to 'user'. The row is durable immediately; if the server crashes now, the keystroke survives.
  3. Schedule a debounced markdown flush. scheduleMarkdownFlush(tabId, document) sets a 1-second timer (per tab) to serialize the Y.Doc and writeFileSync the workspace file. If another update lands within the window, the timer resets. Reading from disk is not the hot path — the server always answers reads from the Y.Doc, not the file.
Section 6 · Data flow

Flow: triggering an agent render

A render is one agent turn. Something in the browser calls submit(), which POSTs to /api/render. The server runs one streaming query() call; the agent uses custom MCP tools to read and write the live Y.Docs; events flow back over SSE.

What can trigger a render

Any of these ends up calling submit(). The trigger only determines the user-message string.

TriggerWhat the user diduserMessage sent
Idle timeoutTyped, then paused 3 secondsEmpty. Server substitutes "the user clicked Wake-up without a specific request."
Keyboard shortcutCmd/Ctrl + EnterEmpty (same as idle, but no wait).
Wake buttonClicked the cat in the agent dockEmpty.
Selection feedbackSelected text, picked a pinned action or typed a note in the popupThe action label / note, plus the excerpt and range as context.
Direct messageOpened the agent dock composer and typed a requestWhatever they typed.

What the POST body contains

POST /api/render
{
  userMessage: string      // empty for idle / wake-up, or the user's prompt
  model:       'opus' | 'sonnet' | 'haiku'
  tab:         string      // which tab is active
  warmup?:     boolean     // optional prefetch flag
}

Rules, references, agency, and tab content are not in the POST body. The server reads rules / agentSettings from state.json, tab content from the live Hocuspocus Document, and per-tab "last seen" markdown from the kv table. Add a rule mid-session and the next render sees it automatically.

Step-by-step

  1. Browser calls POST /api/render. The response is an SSE stream.
  2. Server reads live content + "last seen" from each open tab.

    For every open tab, readLiveTabMarkdown(tabId) serializes the live Hocuspocus Document (falling back to the registry Y.Doc if no client has connected yet). kv['last_seen:<tabId>'] holds the content the agent saw at the end of the previous render; a unified-line diff against current content is what surfaces "I fixed a typo" or "I reverted that rewrite" to the agent.

  3. Server builds one multi-tab prompt.

    Assembled in buildMultiTabPrompt(). Inlining policy:

    • Active tab: full content inlined + diff against last_seen.
    • Non-active tab with changes: path + diff only; agent calls read_doc for full content.
    • Non-active tab, unchanged since last render: path only.
    • First-render tab (no last_seen): full content inlined.

    Plus: persistent writing rules, style-references index, agency guidance (conservative / balanced / aggressive), tool-usage rules, and MCP tool definitions for propose_rule / propose_hook.

  4. Server calls query() with two MCP servers registered.

    docwriter — propose_rule, propose_hook.
    docwriter-doc — edit_doc, read_doc, write_doc.

    Built-in Read / Glob / Grep are available for exploring the workspace. Built-in Edit / Write are still registered but the prompt forbids their use on open-tab paths — scratch paths under .docwriter/agent/scratch/ may use either channel.

  5. Agent calls edit_doc({ path, old_string, new_string }).

    In mcp-doc-tools.ts:

    1. Route by path. Scratch → fs.writeFileSync. Otherwise resolve tabId via path-router.ts; reject with isError: true if not an open tab or a scratch path.
    2. getHocuspocus().openDirectConnection(tabId).
    3. Inside the direct.transact(document => ...), serialize the current Y.Doc to markdown and find the single occurrence of old_string. Zero matches or multiple matches → return isError: true with a helpful message steering the agent to read_doc.
    4. In one document.transact(() => { ... }, AGENT_ORIGIN):
      • Rebuild the default XmlFragment via a headless Tiptap Collaboration editor bound to the document — ySyncPlugin emits the minimal Yjs ops inside our transact so they all carry AGENT_ORIGIN.
      • Append a PendingReviewRound to Y.Map('review').pendingRounds.

    Because both side-effects are inside one transact, the resulting Yjs update is atomic. Every connected browser receives the content change and the review card together — it's not possible to see one without the other.

  6. Hocuspocus's onChange fires. The transaction origin is the string 'agent', so the row in yjs_updates is tagged accordingly. The update streams to every connected browser Y.Doc. The server-side UndoManager captures a stack frame because 'agent' is in its tracked-origin set.
  7. Browser sees the update. HocuspocusProvider applies it. The ySyncPlugin translates the Y.Doc change into a ProseMirror transaction; the editor re-renders. The review map mutation triggers Svelte reactivity; the review card appears in the OutlinePane.
  8. SSE stream carries status events throughout.

    Event kinds: tool_call_start, tool_call, assistant_text, assistant_thinking, rule_proposal, hook_proposal, ask_user, notification, cost, subagent lifecycle, and finally result. The result event no longer carries markdown — the content changes already reached the browser through the WebSocket.

  9. After result, update kv['last_seen:<tabId>']. For every tab the agent saw, store the current serialized markdown. The next render's prompt will compute its diff against this baseline.
Section 7 · Data flow

Flow: review & accept/reject

Every edit_doc/write_doc call creates one PendingReviewRound in Y.Map('review').pendingRounds, in the same transaction as the content change. Accept and Reject are pure Y.Map / UndoManager operations; there's no longer a POST /api/document round-trip.

What a review round contains

PendingReviewRound {
  id            // stable uuid for client-side ordering
  beforeMd      // serialized markdown at the start of this tool call
  afterMd       // serialized markdown at the end of this tool call
  trigger       // 'agent_edit_doc' | 'agent_write_doc' | ...
  timestamp
  kind          // 'tiny' | 'big'  — UI treatment
  stepCount     // always 1 in the new model (one tool call = one Yjs txn)
}

stepCount is historical from the streaming-apply era. With direct MCP tools, each call is one atomic transaction, so it's always 1. The Reject path still multiplies undo calls by stepCount for forward compatibility.

Accept
  • Drop the round (and any later rounds up to the one being accepted) from Y.Map('review').pendingRounds.
  • Leave the content unchanged in the live Y.Doc.
  • The mutation propagates through Hocuspocus to every connected client. No server endpoint.
Reject
  • Per-tab Y.UndoManager (client-side mirror of the server's) tracks only AGENT_ORIGIN transactions.
  • Call undoManager.undo() stepCount times — rewinds exactly this round's agent ops. User edits made in between are unaffected (they're not in the tracked-origin set).
  • Remove the rejected round (and any later rounds built on it) from the review map.
  • Trigger a follow-up render with the rejection diff as context so the agent doesn't repeat the rejected edit.
Why this is simpler than before

Accept and Reject used to hit POST /api/document to clean up shadow files. They no longer need to — there's no shadow to clean up. The review round is just a Yjs map entry in the same Y.Doc as the editor content; mutating or removing it is a normal CRDT operation that syncs to every client automatically.

Section 8 · Data flow

Flow: "old_string not found"

With a single authoritative Y.Doc, there's no post-hoc merge to fail. The only remaining conflict is at edit_doc time: the agent formed its plan against a snapshot of the document and, by the time its MCP call executes, the user has edited that region. The literal old_string no longer exists.

  1. Agent planned against content X. It may have seen X via the prompt's inlined content, an earlier read_doc call, or its own prior edit_doc result.
  2. User typed, changing the region of interest. The keystrokes are already in the server Y.Doc.
  3. Agent calls edit_doc({ old_string, ... }). The server opens a DirectConnection, serializes the live Y.Doc, and counts occurrences of old_string.
  4. Zero matches (or >1) → isError: true. The error message tells the agent to call read_doc(path) and retry against the fresh content. No automatic app-level retry — the agent's own tool loop handles it, typically in the next turn.
Design call

The old 3-way merge tried to salvage partial edits when the agent and user overlapped. In the new architecture, the atomic old_string-match check serves the same goal more simply: if the region has changed, the edit is rejected outright and the agent re-plans against current state. User keystrokes are never overwritten because the match never succeeds.

Section 9 · Design

Undo across a server restart

The per-tab server-side Y.UndoManager is the machinery behind Reject. It must correctly reconstruct its undo stack after the Node process dies and restarts, because pending rounds persist across restarts and the user expects Reject to work on them.

The critical ordering

In src/lib/server/ydoc-registry.ts: 

function getTabYDoc(tabId) {
  const ydoc = new Y.Doc();

  // Step 1 — attach UndoManager FIRST.
  const undoManager = new Y.UndoManager(
    ydoc.getXmlFragment('default'),
    { trackedOrigins: new Set([AGENT_ORIGIN]) }
  );

  // Step 2 — THEN replay the persisted updates. Each row's origin is
  // restored via ydoc.transact(..., row.origin), so agent-origin
  // transactions from prior sessions fire through the already-attached
  // UndoManager observer and repopulate its undo stack.
  replayUpdatesInto(ydoc, tabId);

  return { ydoc, undoManager, reviewMap: ydoc.getMap('review') };
}

Swap steps 1 and 2 and the UndoManager never observes the replayed transactions. The undo stack is empty at cold start, and Reject on any pending round silently does nothing. This is the whole content of "Phase 7" of the refactor; the fix is one reordering.

Why it works

Every writer — browser WebSocket, DirectConnection, cold-start seed — records its update with an origin string in yjs_updates. On replay, ydoc.transact(() => applyUpdate(...), row.origin) reinstates both the CRDT state and the origin tag. The UndoManager's origin-based filter sees the same sequence of transactions it would have seen if the server had been running all along.

Cold start path

On getTabYDoc(tabId): construct Y.Doc, attach UndoManager, then replay every yjs_updates row through ydoc.transact(..., row.origin). If there are no rows, seed from the workspace file (origin 'system') and persist that seed as a single row so future loads skip the disk read.

Section 11

Y.Doc registry & review internals

The server registry (src/lib/server/ydoc-registry.ts)

interface TabYDocEntry {
  ydoc: Y.Doc;
  undoManager: Y.UndoManager;  // trackedOrigins: { 'agent' }
  reviewMap: Y.Map<unknown>;    // ydoc.getMap('review')
}

One entry per tab. Constructed lazily on first getTabYDoc(tabId) call. destroyTabYDoc(tabId) tears it down (tab deleted / explicit unload); the persisted yjs_updates rows are not touched.

The Hocuspocus plumbing (src/lib/server/ws-server.ts)

  1. onLoadDocument({ documentName: tabId }) returns getTabYDoc(tabId).ydoc. Hocuspocus copies its state into its own Document and holds that going forward.
  2. onChange({ update, transactionOrigin, document })
    • Resolve origin: if transactionOrigin is a string ('agent' from a DirectConnection, or 'system'), use it. Otherwise (browser Connection instance, context-supplied origin) default to 'user'.
    • appendUpdate(tabId, update, origin) — one row into yjs_updates.
    • scheduleMarkdownFlush(tabId, document) — pass the live document from the payload (NOT the registry Y.Doc), because the registry one is stale.

The custom MCP tools (src/lib/server/mcp-doc-tools.ts)

  1. Path routing. Scratch paths → fall through to fs (no Y.Doc involvement). Workspace tab paths → resolveTabFromPath + isOpenTab. Unknown → isError: true.
  2. getHocuspocus().openDirectConnection(tabId). Returns a handle whose transact(cb) method invokes the callback against the live Document. cb receives the Y.Doc.
  3. Inside direct.transact(document => ...):
    • Serialize the current markdown (serializeYDocToMarkdown(document, kind)).
    • edit_doc-specific: count old_string matches; 0 or >1 → early-return without mutating.
    • Open an inner document.transact(() => { ... }, AGENT_ORIGIN):
      • Bind a headless Tiptap Editor with Collaboration pointing at this document + field 'default'.
      • Call headless.commands.setContent(newMd, { emitUpdate: false }). ySyncPlugin translates the ProseMirror diff to minimal Yjs ops on the fragment; all inside our transact, so they all carry AGENT_ORIGIN.
      • Destroy the headless editor.
      • Append to reviewMap.get('pendingRounds').

Client-side review (src/routes/+page.svelte)

pendingReviewRounds is a Svelte store mirroring the active tab's Y.Map('review').pendingRounds. An observer on the Y.Map updates the store whenever the map changes — whether from a local mutation, a remote client, or an agent edit.

Accept: reviewMap.set('pendingRounds', rounds.slice(idx + 1)). Reject: for (let i = 0; i < round.stepCount; i++) undoManager.undo(), then the same map write. No fetch() anywhere.

Undo isolation

Per-tab Y.UndoManager with trackedOrigins: new Set([AGENT_ORIGIN]) and captureTimeout: 0. Each agent-origin transaction is its own undo step. User keystrokes (default origin) never enter the stack, so they survive Reject.

The client has its own per-tab UndoManager (src/lib/yjs-agent.ts) that mirrors the server's, so Reject operates locally and immediately. Its stack is reconstructed from replayed Y.Doc history the next time the tab's Y.Doc is synced from the server.

Section 14

Workspace safety

File APIs all route through src/lib/server/workspace-path.ts, which resolves any request path and validates it stays inside DOCWRITER_ROOT.

  • Path traversal (../../etc/passwd) is rejected.
  • Symlink escapes are blocked — even for paths that don't exist yet, the resolver walks up to the nearest existing ancestor, resolves its real path, and checks containment from there.
  • Hook configuration is never agent-writable. The agent can only propose hooks via the propose_hook MCP tool; acceptance flows through the user and PUT /api/hooks.
  • write_doc never creates new tabs. The target must already be open (so the user has explicitly opted in to letting the agent write there).

Bottom line

DocWriter is a local, multi-file writing environment with per-tab CRDT editor state held authoritatively on the server and synced over WebSocket, an append-only SQLite log of every Yjs update, and a Claude Agent SDK loop that edits the live Y.Doc through custom MCP tools. Content convergence is the CRDT's job; review, undo, and reject all fall out of origin-tagged transactions on a single Y.Doc.
